## What This Is

A publishing and social platform for writers and readers, built on the Nostr protocol. Writers own their identity, audience, and content via custodial Nostr keypairs. Readers pay via a shared "reading tab" (Stripe-based accrual → payout flow).

## Development & deployment

This is a local dev directory on the developer's laptop. Test features at `localhost:3010` (web) and `localhost:3000` (API). To deploy to production: push to git, then the developer SSHs to a remote server and rebuilds there. Claude Code has no direct access to the production server.

**A push is a ship, and the beta is closed.** The developer pulls and deploys whatever was pushed at the end of **every** session, so master is live by the next one — never write a "pending prod deploy" tracker item (that claim is stale before anyone reads it; write the deploy *requirements* in the session's closing response instead), and never push work meaning to finish it next session. And with **essentially no real active members yet**, a bad deploy costs a fix-forward commit rather than an incident: ship on `tsc` + root ESLint + `next build` + a smoke, keep exhaustive browser/DB verification for **money and data** paths, and stop paying for deploy-window safety (both-orderings migrations, dark-ship brakes) except where a real external system — Stripe above all — is on the other side. **Unchanged by beta size:** the money/ledger invariants below, anything that can destroy data, and Stripe. All of this inverts the day the beta opens.

### Database migrations

Migrations are numbered SQL files in `migrations/`, applied in numeric-prefix order by the sole runner `shared/src/db/migrate.ts` (`npx tsx shared/src/db/migrate.ts` from the repo root — it resolves `migrations/` from cwd; there are no per-service runners). The runner records a sha256 per applied migration and verifies them on every run — editing an already-applied file is fatal (corrections go in a NEW migration); the `_migrations.checksum` column is runner-owned bootstrap DDL, never a migration file.

**A `CONCURRENTLY` migration must be exactly one statement** — the runner refuses it otherwise (`migrate.ts`, 2026-07-20). Postgres sends a multi-statement file as one simple query and wraps it in an *implicit* transaction block, which is precisely what `CREATE/DROP INDEX CONCURRENTLY` refuses; put the other statements in a separate migration. The runner picks the no-transaction path by matching a **comment-stripped** copy, so prose mentioning `CONCURRENTLY` no longer silently costs a migration its rollback (migrations 022/083 were live misroutes). `ALTER TYPE … ADD VALUE` also takes that path — conservatively: PG12+ permits it inside a transaction, but the new value can't be *used* until commit.

**`schema.sql` is the genesis base, not a derivative.** A fresh DB (dev `initdb.d` and prod) boots from `schema.sql`, *then* `migrate.ts` applies anything newer. So `schema.sql` must already contain every migration's effect **and** seed `_migrations` with every migration filename (so `migrate.ts` is a clean no-op on fresh boot). There is no genesis migration — migration `001` ALTERs tables only `schema.sql` creates — so the chain can't be replayed from empty; `schema.sql` is load-bearing.

After adding a migration or changing the schema, regenerate `schema.sql` with `pg_dump --exclude-schema=graphile_worker` from a fully-migrated DB (never hand-edit — that breaks canonical round-trip; graphile-worker owns its schema lifecycle end-to-end, and a baked-in structure-only copy crash-loops the worker on fresh boot — see the drift-guard header), re-append the `_migrations` seed in the same step, then run the drift guard:

```bash
scripts/check-schema-drift.sh   # 0: seed lists all migrations · 4a: no migration seeds platform_config · 3: every migration-created object is in schema.sql · 1: migrate is a no-op on a schema.sql DB · 3b: every migration-created INDEX means the same thing in schema.sql · 4b/4c: a fresh DB carries every config dial, and config-defaults.sql covers every historical seed · 2: schema.sql round-trips clean
```

It builds throwaway DBs in the dev Postgres container (read-only w.r.t. your real dev DB) for Checks 1/3b/2; Checks 0/3 are pure-text and need no DB. **CI-enforced** (`.github/workflows/ci.yml` `schema` job). It catches a missing seed entry (Check 0), non-canonical hand-edits (Check 2), and — Check 3 (object presence, exit 3) — a seeded filename whose **object body** (table/index/type/function/trigger/view) was omitted from `schema.sql`, which Checks 0/1/2 all pass green on (migrate skips the seeded migration, so the object is never created and nothing notices). Check 3 is name-grep against the migration's net-surviving CREATE set (drops + `RENAME TO` netted out in chronological order). Never hand-edit the seed line.

**A seeded migration never runs, so `schema.sql` — not the migration file — is what every database actually has.** A migration's stated intent is therefore not evidence its effect is in force, and the gap between the two is silent in both directions: the object can be *absent* (Check 3) or *present under the same name meaning something else* (Check 3b, added 2026-08-05 after `idx_notifications_dedup` spent three years non-partial on every DB including prod, because migration 019 made it partial and `schema.sql` did not — Checks 0/1/2/3 all green throughout). **3b compares definitions rather than names, and it is INDEXES only** — Postgres canonicalises both sides (execute the migration's own CREATE under a probe name, diff `pg_get_indexdef()`), which works because an index is created whole and never ALTERed; a table's `CREATE TABLE` accumulates later `ADD COLUMN`/`ALTER TYPE`/`ADD CONSTRAINT`, so the same comparison would false-positive on every table the chain has touched. It reads the LAST surviving CREATE per name, so a later migration that legitimately rebuilds an index defines it. The guard's residual gap is now **column-level** drift alone (`ADD COLUMN` missing from `schema.sql`) — there the mechanical pg_dump-and-re-append-in-one-step discipline is still what closes it.

## Architecture

Browser → Nginx (80/443) → `/api/*` to gateway, `/` to web. The Next.js app rewrites `/api/*` to `GATEWAY_URL`; the frontend never calls backend services directly.

Orientation only (the cited ADRs / code are the source of truth):

- **Auth**: magic links + Google OAuth (no passwords); httpOnly JWT cookies set by the gateway. `gateway/src/middleware/auth.ts` exports `requireAuth` / `optionalAuth`. Custodial Nostr keypairs: key-custody holds private keys; key-service wraps/issues NIP-44 keys to readers for gated content.
- **Nostr**: articles are kind 30023 (NIP-23) replaceable events signed via key-custody; the platform runs its own strfry relay. **The web client holds no relay connections** — `web/src/lib/ndk.ts` is types-only and all content arrives over the gateway REST API (so a card tree that unmounts tears down nothing and refetches nothing; that is what makes workspace virtualization cheap). Soft-delete publishes a kind 5 tombstone.
- **Payments**: readers accrue a Stripe tab as they read gated articles; payouts via Stripe Connect (`payment-service/src/services/`). Article access logic in `gateway/src/services/article-access/`; `/articles/:id/gate-pass` is a thin wrapper over `performGatePass()`.
- **Media**: `gateway/src/services/media-store.ts::storeImage(uploaderId, buffer)` is the **one path from image bytes to a public URL** — crunch to WebP, hash, dedupe on `sha256`, sign a kind-24242 BUD-02 auth with the uploader's custodial key, PUT the blob to the internal **Blossom** blob store (pinned `6.2.0`), verify the returned hash, then insert `media_uploads` — never write that table or PUT to Blossom outside it, since the hash check before the INSERT is what stops the table claiming a blob the store does not have. `gateway/src/routes/media.ts` owns only what is about the *request* (multipart, the declared-MIME allow-list, status codes); `sharp` inside `storeImage` is what validates the bytes really are an image, which is the check a caller holding a third-party buffer needs. nginx proxies `/media/<sha256>.webp` → Blossom **read-only** (quoted-regex hash-shaped path + `limit_except GET`; Blossom's BUD-02 auth accepts any self-signed event, so internal-only reachability IS its access control — never widen the proxy to its upload/delete endpoints). Public URL scheme (`PUBLIC_MEDIA_URL/<sha256>.webp`) is backend-independent. The legacy `media_data` disk volume is retained one soak cycle for rollback of pre-cutover blobs only (post-cutover blobs live solely in Blossom; Phase 4 removes the volume + the dead disk code). oEmbed proxied in the same route. Spec: `docs/adr/ADR-blossom-migration.md`.
- **Editor**: TipTap (`web/src/components/editor/`) with a paywall gate node; markdown via `tiptap-markdown`.
- **Feed & search**: full-text search via `pg_trgm` (`gateway/src/routes/search.ts`); feed ranking is Phase 1 only, and its spec is **archived** (`planning-archive/FEED-ALGORITHM.md`) — read it as history, not as the live design.
- **External feeds (Universal Feed)**: RSS/Atom/JSON, external Nostr, Bluesky, Mastodon/Lemmy/threadiverse, and email are ingested by `feed-ingest/` (Graphile Worker + Jetstream listener; adapters in `feed-ingest/src/adapters/`). Data model `external_sources`/`external_subscriptions`/`external_items`, denormalised into the unified `feed_items` timeline by transactional dual-write (each row carries `post_id`, `version`, `biddability_tier`). **External subscriptions are feed-derived** (see Invariants): an `external_subscriptions` row exists iff the source sits in ≥1 of the owner's feeds, maintained by `addSource`/`removeSource` in `gateway/src/routes/feeds/sources.ts`; it doubles as the external follow-graph (kind-3 follow list, author Following state). The standalone subscription CRUD + Subscriptions page were retired (migration 116 dropped per-sub `is_muted`/`daily_cap`); `gateway/src/routes/external-feeds.ts` now holds only admin diagnostics, and per-feed mute is `feed_sources.muted_at`. Source authoring via the workspace feed endpoints (`POST /workspace/feeds/:id/sources`, protocols `rss`/`nostr_external`/`atproto`/`activitypub`). Live workspace reads via `GET /workspace/feeds/:id/items` (+ `GET /thread/:postId` projector). Spec: `docs/adr/UNIVERSAL-FEED-ADR.md`; workspace full view: `docs/adr/WORKSPACE-FULL-VIEW-SPEC.md`.
- **Trust graph** (**parked** — the backend runs, the surface does not: the card `TrustPip` is currently a decorative dot that opens nothing, see *Feed card chassis*): Layer 1 (`trust_layer1`, daily cron) + `trust_polls` compose the four-state glyph (`feed-ingest/src/lib/trust-pip.ts`). Layer 2 vouches (`vouches`/`trust_profiles`/`trust_epochs`); Layer 4 relational ("N writers you follow endorse this"). Gateway `trust.ts`; UI `/network?tab=vouches`; `TRUST_DRY_RUN=1` for dry runs. Spec: `docs/adr/ALLHAUS-OMNIBUS.md`.
- **Owner dashboard**: the operator surface at `/admin/*` (chromeless standalone pages; seven tabs incl. the moderation Reports page and the closed-beta Waitlist) backed by `gateway/src/routes/admin-dashboard.ts`. `requireAdmin`/`getAdminIds` live in `gateway/src/middleware/admin.ts` (the one home — moderation and external-feeds import from there, never re-implement). Money numbers read the ledger `SUM()` views (outstanding writer money = `ledger_writer_earned` − `ledger_writer_earnings`); the config editor updates **existing** `platform_config` keys only (new dials via `config-defaults.sql` per the tuning-dials invariant) and refuses the runtime-state keys (`payouts_halted`, `jetstream_healthy`); the regulatory tax thresholds are themselves dials, fallbacks tripwired by `gateway/tests/admin-dashboard.test.ts`. Spec: `planning-archive/OWNER-DASHBOARD-SPEC.md` (adapted; FIX-PROGRAMME 2026-07-22).

### Invariants (these are rules, not orientation)

- **One server-side article publisher**: `gateway/src/services/article-publisher.ts::publishPersonalArticle` is the sole server-side path that publishes a personal article — sign v1 via key-custody, `articles` + `feed_items` dual-write and the outbox enqueue in ONE transaction, then the vault seal and v2 swing. The scheduler is a caller, not the owner; a bulk caller (archive import) is the second. **Never write a second publisher beside it** — a copy that drops the in-transaction enqueue or the vault step is exactly the relay-outbox and paywall-deliverability bug class. Its options (`publishedAt`/`sendEmail`/`matchDrives`) all default to the scheduler's behaviour, so an omitted option can never change a scheduled publish. **The date is a split, not one value**: `published_at` (the `articles` column, the `feed_items` column AND the NIP-23 tag) is *first publication* and may be backdated; the event's `created_at` is *when it was signed* and stays now. Wiring both to the backdate reads as more consistent and is worse — past strfry's `rejectEventsOlderThanSeconds` (ten years, `relay/strfry.conf`) the article row indexes cleanly and the relay publish silently fails. Spec: `docs/adr/ARCHIVE-IMPORT-ADR.md` §II/§III.
- **Relay outbox**: every write path that publishes a signed Nostr event enqueues into `relay_outbox` inside the caller's transaction (`shared/src/lib/relay-outbox.ts::enqueueRelayPublish`); the `feed-ingest` `relay_publish` worker owns publish + retry. So `POST /sign-and-publish` and the publication publish routes mean "signed and durably queued", not "on relay" — relay blips become invisible worker retries, not 5xx. Spec: `docs/adr/RELAY-OUTBOX-ADR.md` (+ `RELAY-OUTBOX-PHASE-4-ADR.md`).
- **Money ledger**: every money MOVEMENT posts a signed `ledger_entries` row via `shared/src/lib/ledger.ts::recordLedger(client, …)` **inside the same transaction** as the table write it records (same pattern as `enqueueRelayPublish`) — a write that forgets it silently under-reports. The registered money-path set, the raw-balance-write ban and the no-new-unregistered-site rule are CI-enforced by `scripts/check-ledger-adjacency.sh` (CI `backend` job), **whose header is the authority on the rule, the two funnels and the residual gap** — read it there rather than restating it here. Its per-file call-site floors are hand-read counts: **re-read them, never derive them.** Specs: `docs/adr/FUNDS-SEGREGATION-INTEGRATION.md` §10 · `docs/audits/WRITER-SIDE-LEDGER-CUTOVER.md` · `docs/audits/allhaus-logic-economy-audit.md`.
  - **`applyLedgerDelta` is the only writer of `reading_tabs.balance_pence`** (`ledger.ts`, PAYMENTS ADR §1.8): it moves the column and posts the mirror entry as one indivisible, unclamped pair, so the sign is *derived* and a caller cannot mismatch them. Its contract: upserts by `reader_id` (create-or-update, for tab-less dispute/pledge/subscription accounts), takes no `FOR UPDATE` (a caller needing lock-ordering keeps its own prior lock — e.g. `confirmSettlement`), returns `{ledgerId, balancePence, tabId}`; raw `balance_pence` UPDATEs are banned outside it (adjacency Guard 2). An extra non-tab entry alongside (subscription `subscription_earning`) stays a plain `recordLedger`.
  - **The balance is allowed to go negative** (negative = platform owes reader / pre-paid credit). Clamping it while the ledger posts the full amount is the divergence bug class, abolished by construction above.
  - **The ledger is append-only** (DB guards on row UPDATE/DELETE and `BEFORE TRUNCATE … FOR EACH STATEMENT`): corrections are reversing entries, never UPDATE/DELETE/TRUNCATE.
  - **Sign convention** (in `ledger.ts`): reader-tab entries mirror **every** `balance_pence` movement, in either direction — accrual/pledge **−amount**, settlement **+settled**, spend→subscription credit-back **+credit** (`subscription_credit`), subscription charge **−price** (`subscription_charge`, via `logSubscriptionCharge`) — so `balance == −SUM`. Writer/member payout entries are **+amount** with a `NULL` counterparty. Platform is never an `account_id` (that column is `NOT NULL`); it is always the `NULL` counterparty, so platform fee / behaviour-tax is *implicit*.
  - **Payout children** (funds segregation, dark behind `STRIPE_ALLOCATED_FUNDS`): a payout is N child transfers, so `payout_transfers` is in `PAYOUT_MARKER` and any future writer of it must be registered. The child's ledger entry posts **per child, inside that child's `pending → completed` flip transaction, gated on the flip's `rowCount`** — never once at parent completion for the parent's full amount — and its `(ref_table, ref_id)` stays the **PARENT** row (`ledger_publication_distribution` filters `ref_table = 'publication_payout_splits'`, and reconcile-ledger's `ledger_orphans` ends in a default-deny catch-all that halts ALL payouts on an unknown reversal `ref_table`). All three cycles run on that lifecycle: the publication parent is the *split*, whose `advanceUnits`/`releaseUnits` are no-ops by design (a split owns no claim rows, and a failed split keeps its claim for manual re-pay), and a tribute unit is one accrual at **fee 0** (an accrual is already carved out of the author's post-fee net).
  - **A `ChildCycleSpec.postLedger` that reads the state its own `advanceUnits` is about to change must read it FIRST, and say so** — `executePendingChildren` posts the ledger then advances, in that order, inside one transaction. The tribute carve sums the child's accruals at `state = 'released'`; read one transition later it sums 0 and the author silently keeps earnings that left them. Both statements are exported, and the DB test runs them in order with the post-advance figure as a paired control.
  - **A ledger entry needs a single-shot gate that is a state transition's own `rowCount`** — a child entry rides the `pending → completed` flip, the carve-zeroed accruals ride `TRIBUTE_CHILDLESS_ADVANCE_SQL`'s `RETURNING`. `completeParentIfSettled` cannot supply one (it reports `completed` from a tally, not from its UPDATE), so never hang a ledger post on it.
  - **A publication payout completes on "no split PENDING"**, never "every split completed" — the latter freezes a parent forever on one failed split, since the resume sweep retries only `pending` ones (one home: `PUBLICATION_PAYOUT_COMPLETE_SQL`).
  - **A reconciliation check declares its `severity`, and an alert-tier one never touches `haltPayouts`** (`reconcile-ledger.ts`; `CRITICAL_CHECKS` is five `'halt'` checks — incl. the `ledger_orphans` default-deny catch-all — plus one `'alert'`). `'halt'` means the ledger and its column DISAGREE: money leaving on books that don't balance is money we can't account for, so all three cycles freeze. `'alert'` means the books AGREE about a state that must not persist — `negative_reader_tab`, a reading tab in credit, which `reader_balance_parity` passes over in silence *because* it reconciles (that is how the August 2026 double-charge went unalerted). Freezing every Writer's payout over one Reader's credit would itself be the ¶7.14.6 principal-like-control marker `PAYMENT-PERIMETER-ADR` W1 exists to narrow, so it alerts under its **own** marker (`alert` = the check name, a separate `DEPLOYMENT.md` alert from `payouts_halted`) and moves nobody's money. Two corollaries: a violation carries `truncated`, because for an alert-tier check the payload IS the response and a capped sample reading as a total is the silence the check exists to end (W4's per-account halting attribution must go further and run **uncapped** — halting from a truncated payload silently pays the 21st diverging account); and **an alert-only check must not ride `allocation-reconcile.ts`**, whose `runAllocationReconcile` short-circuits on `allocatedFundsEnabled()` and would make it a silent no-op for exactly as long as `STRIPE_ALLOCATED_FUNDS` ships dark. Response runbook: `docs/runbooks/reader-tab-credit.md` — **which resolution applies depends on the cause, and one of the three causes must not be "resolved" at all** (the spend→subscription conversion produces a Reader-funded negative tab by design; open owner decision, ADR W1).
  - **Allocation reconciliation ALERTS, never halts, and lives OUTSIDE `reconcile-ledger.ts`** (`payment-service/src/services/allocation-reconcile.ts`): neither thing segregation measures is a reason to stop paying anyone — a stale budget makes the packer under-draw by construction, and a high residual means the money is right and the *coverage* is poor. `haltPayouts` stays reserved for the `'halt'`-tier reader-tab divergences above. `allocated_draws` is a drawing budget, **not** a ledger — it mirrors no entry and posts no movement, so its `GREATEST(0, …)` is not the banned clamp; a `charge.refunded` (both arms — the PARTIAL one is the wedge) posts a `kind='refund'` draw carrying Stripe's CUMULATIVE `amount_refunded`, upserted with **GREATEST, never assignment**, because webhook delivery is unordered.
  - **A rate with an empty denominator is reported ABSENT, never as zero** — and where the population carries an *unmeasured* arm, that arm is its own reported figure and joins neither side of the ratio. No measurement is not a good measurement, and this class always lies in the reassuring direction: a residual share over a window with no payouts reads as perfect segregation on a platform whose payout cycle has silently stopped, and a coverage share over settlements nobody has read back reads as *nothing is segregated* every day the flag ships dark. Both return `null` and the caller renders the absence **in words** (`summariseResidual` / `summariseCoverage`, `payment-service/src/services/allocation-{reconcile,coverage}.ts`). The tri-state trap is the same rule one level down: `tab_settlements.allocated_pence` NULL ("never synced") and 0 ("synced, Stripe held nothing") are **opposite** facts, so the unallocated predicate is `allocation_synced_at IS NOT NULL AND allocated_pence = 0` and never a bare `IS NULL`, and the never-synced count ships beside the share so one computed over a partial sample cannot read as one over all of it. Spec: `docs/adr/PAYMENT-PERIMETER-ADR.md` W2.
  - **Balances are the `SUM()` read-model views**, reconciled by `scripts/reconcile-ledger.sql`. Reader balance is `ledger_reader_balance` (counting `subscription_credit`/`opening_balance`; `GET /my/tab` reads it), while `reading_tabs.balance_pence` is **retained as the locked operational running total** settlement reserves against (`SELECT … FOR UPDATE`) — display reads the ledger, settlement reads/locks the column, and dropping the column needs a settlement-concurrency redesign. Writer EARNING is `ledger_writer_earned` (`writer_accrual`/`writer_accrual_reversal`/`tribute_carve`/`tribute_carve_reversal`/`subscription_earning`), **disjoint** from the paid-out `ledger_writer_earnings`; `getWriterEarnings().earningsTotalPence` reads it. `writer_accrual` (+read_net, account=writer / cp=reader) posts per read at settlement; `tribute_carve` (−root gross, account=author / cp=root inspirer) debits the author when a ROOT tribute's carve is *paid* — the single point the redirected share enters the ledger. **Writer-earnings parity is the standing ledger gate.** The pending/paid sub-split stays `read_events`-derived (the ledger doesn't model that distinction), and **publication-distribution reads were NOT cut over** (still reconciliation-only).
  - **The publication pool and the individual writer cycle are exact complements, both keyed on the denormalised `read_events.publication_id`** — never `articles.publication_id` (an article moving publications must not re-home its historical reads). Publication reads are excluded from the writer cycle's eligibility/recompute/claim and from the personal `writer_accrual` + earnings displays; the pool claims them, **plus** publication SUBSCRIPTION earnings (settled-gated like every claim), the sub net joining **post-fee** — already net (fee floored per charge), never through the pooled-fee formula — recorded on `publication_payouts.sub_net_pence` and kept out of `total_pool_pence`, so the chargeback proration denominator (`total_pool_pence + sub_net_pence`) dilutes a read's share instead of reversing sub-derived split money. A charged-back publication read reverses across the paying payout's PAID `publication_payout_splits`, prorated by read-gross÷pool, via `writer_payout_reversal` — never against the author. Splits are a fixed share of the 10000 base (platform keeps any unallocated remainder) with `SUM(bps) ≤ 10000` enforced at write time; `computePublicationSplits` clamps standing bps cumulatively at 10000, write paths serialise under the `pub_shares` advisory lock, and invite re-accept zeroes a resurrected member's stale share.
  - **Subscriptions are collection-gated**: a subscription charge is pure tab debt, so subscribe/reactivate require a card on file (402 `card_required`) and a card-less renewal expires instead of charging. `subscription_events.settled_at` is the subscription twin of `read_events.state='platform_settled'` (stamped by `confirmSettlement`, or at charge time when pre-paid credit covers it), and the payout cycle claims **only stamped earnings** — never reintroduce an ungated claim. A threshold settlement sweep in the settlement-reconcile cycle collects tab debt that accrues with no gate pass.
  - **Tributes are consent-gated, forward-only accrual** (Dial A): no `held`/`swept`/`returned` states — an accrual exists only for a `live` (consented + onboarded) tribute and starts `released`; settlement freezes a share only for a `live` tribute; `tribute_carve` fires only on a `live` root's paid share. The one remaining `TRIBUTES_ENABLED` gate is compliance residual #1 (`docs/adr/UPSTREAM-EDGES-BUILD-PLAN.md` › *Dial-A rework*).
  - **A notification binds its target, and its target column is in the dedup index**: every `INSERT INTO notifications` is a bare `ON CONFLICT DO NOTHING` with no inference target (~20 sites), so `idx_notifications_dedup` **alone** decides what collapses — and it can only tell two notifications apart by a column it actually contains. A type that sets no reference column therefore dedups across *every* target: two different gifts (migration 172) or two different drives (174) read as one notification and the second is silently dropped. - **Stripe money-moving creates — terminal vs ambiguous**: every Stripe call that creates a money-moving resource (`paymentIntents.create` for settlement, `transfers.create` for writer/tribute/publication payouts) uses the three-phase reserve→create→confirm pattern with a **row-stable idempotency key**, and MUST wrap the create in try/catch splitting **terminal** (a deterministic rejection that created nothing) from **ambiguous/transient** (connection/API/rate-limit/timeout — the resource may have been created before the response was lost). Terminal → mark the row `failed` and release its claims (settlement: drops `reserveSettlement`'s pending-guard + flags `accounts.card_action_required_at`; payout: rolls back claimed reads/accruals via the shared `rollback*PayoutRows`), then return. Ambiguous → **re-throw** so the resume sweep retries with the SAME key (which dedupes a resource that did go through) — **never roll back on ambiguous**, or you double-charge (settlement) / double-pay (payout). Classifiers in `payment-service/src/lib/charge-errors.ts`: `isTerminalChargeError` (charge: `StripeCardError`∪`StripeInvalidRequestError`) and the deliberately **narrower** `isTerminalTransferError` (transfer: `StripeInvalidRequestError` only — double-pay is the worse failure). A create with no try/catch is the orphan bug class: a stuck-`pending` row whose `*.failed` webhook never matches (keyed on an id that was never stored), frozen forever. **One ambiguous error is RECOVERED, never blind-retried: `StripeIdempotencyError`** (same key, drifted payload — settlement rebuilds its payload per attempt, so a deploy/card-swap/brand-flip conflicts every retry until Stripe GCs the key, ~24h of frozen tab). It proves a first request was recorded, so settlement resolves it by PI lookup — `settlement.ts::recoverIdempotencyConflict`, matching `metadata.settlement_id` via `paymentIntents.list` (**never `.search`** — its index lags, and a lagged miss reads as "provably absent" and re-charges); adopt live / terminal-fail dead / fail-without-card-flag on proven absence / change nothing on a truncated window. Never resolve a conflict by rotating the key or rolling back. The resume sweep alerts (`SETTLEMENT STUCK PENDING`) on any pending row older than one retry cycle. - **A mocked `pool.query` must answer from the SQL it is handed, wherever it can** — and where it can't, the test says so out loud. The repo's route/worker tests mock the DB client and dispatch on the query string; the trap is a mock that returns its fixture *regardless* of the SQL, because then the test is pinning the fixture and the query is unverified (a dropped `::timestamptz` cast and an `ORDER BY` flipped to `ASC` have both passed a green suite this way). The rule has three parts: **(1)** where the answer is derivable from the SQL — sort direction, `LIMIT`, a `WHERE` bound the params carry — derive it (`gateway/tests/admin-waitlist.test.ts` reads the `ORDER BY` out of the query); **(2)** where it genuinely isn't — a cast, a `FILTER`, anything only Postgres can evaluate — assert the SQL's *shape* and comment that it is a structural pin, not a behavioural one (`waitlist-digest.test.ts`); **(3)** the class that survives both is what the DB-backed tests (`skipIf(!DB_URL)`) and driving-it-for-real exist for. **Mutate before believing any of it**: revert the fix, and a test that stays green was pinning the mock. Two corollaries: **the mock must hand out COPIES of its rows, never the live objects** — shared identity lets one request observe another's writes, a snapshot no database would ever give it, which makes a losing racer read as a resend rather than a refused claim; and **a concurrency test must FORCE its interleaving** — left to the event loop the first request runs to completion before the second issues a query, so a test of a claim/lock guard exercises nothing and stays green against a route with no guard at all (hold every racer's read open until all have arrived — `admin-waitlist.test.ts::holdReadsUntil`).
- **A position in a timeline must keep the database's precision**: any value that records *how far we have got* through a time-ordered table — a pagination cursor, a digest watermark, a sweep's high-water mark — and is then fed back into SQL must round-trip at Postgres's own precision, never through a type that holds less. `timestamptz` keeps **microseconds** and a JS `Date` keeps milliseconds (carry it as `created_at::text` and compare with `$1::timestamptz` — `gateway/src/workers/waitlist-digest.ts`); `EXTRACT(EPOCH …)` is **fractional** and `parseInt`/`::bigint` truncate it to whole seconds (hence the one codec, `gateway/src/lib/cursor.ts`). **Truncation always errs backwards**, which is why this bug class ships green: rounding down re-includes the row the marker came from, so the symptom is a duplicate, a repeated digest or a page that never advances — never an error, and never anything a mocked JS `Date`/`number` can reproduce in a unit test. The fix is always to stop converting, not to add tolerance.
- **A recurring boundary is computed from a stored anchor, never from the last one you computed**: a subscription period end — and anything later built the same way — is `anchor + N calendar steps`, not `previous value + one step`. JS `setUTCMonth` **overflows rather than clamps** (31 Jan + 1mo → 3 Mar), so advancing the previous end and then advancing *that* makes the error compound, and the boundary walks away from the day the user agreed to a few days a month. **The anchor cannot be recovered afterwards** — once an end has been clamped to 28 Feb, nothing in the row says the subscription hangs off the 31st — which is why it is a column (`subscriptions.period_anchor_day`, migration 170) and not an inference, for the same reason `accounts.free_allowance_granted_pence` is. One home for the arithmetic, `shared/src/lib/subscription-period.ts`; a fixed 30/365-day millisecond add is not a month or a year and belongs on no create path. Like the precision rule above, this class ships green — it never errors, it just moves. And **a correction is not a backfill**: re-deriving the true anchor for live rows would push a subscriber's next renewal later than the date they have already been told, so existing drift is frozen where it is (migration 170's `UPDATE` reads `current_period_start`, deliberately not `started_at`).
- **A shared secret between services is PROVEN at boot, never assumed** (`gateway/src/lib/internal-parity.ts`): the gateway probes `GET /api/v1/auth-check` on each peer — a route behind that peer's OWN existing internal guard, so reaching it IS the proof and nothing derived from the secret is ever exchanged — and **exits** on a definitive 401/403, naming the peer and the env var. Both secrets, all three peers (`INTERNAL_SERVICE_TOKEN` → payment; `INTERNAL_SECRET` → key-custody + key-service). Three rules, each of which the incident that prompted it would have broken. **(1)** Terminal is `401` **and** `403` — payment answers 403, both key services answer 401, so a 403-only classifier silently never checks the wider `INTERNAL_SECRET` surface *and* passes every test anyone thinks to write. **(2)** Only a definitive rejection is fatal: unreachable, timeout, 5xx and `404` (a peer on an older image) are ambiguous, retried, and never kill the gateway — the same terminal-vs-ambiguous split as the Stripe classifiers, and without it a partial deploy crash-loops the one service that also serves all free reading and auth. **(3)** The probe runs AFTER `listen()` and "never confirmed" (`null`) is a third state distinct from confirmed — collapsing it into "fine" is the failure the check exists to end. Why fatal: a drifted `INTERNAL_SERVICE_TOKEN` on prod (2026-08-07) had payment 403 every gateway call including `/gate-pass`, so **every paywalled unlock failed silently** while the site looked healthy; a failed deploy is the cheaper failure. Adding a new cross-service secret means adding it to `PARITY_PEERS`. **A 5-minute re-probe covers the case boot cannot** — a peer redeployed alone, while the gateway keeps running — and it is **never fatal** (a peer recreated at 3am must not take down free reading and auth with it), reporting instead through three surfaces: gateway `/health` 503 ⇒ `docker compose ps` unhealthy (safe: nothing depends on the gateway with `condition: service_healthy`, and `unless-stopped` doesn't restart on health), one log line **on the transition only**, and a banner atop `/admin/overview`. Its state is **sticky both ways** — only a proven match clears a proven mismatch, and an unreachable peer erases neither, or the signal flaps on every routine restart and gets learned-past. Distinct feature families get distinct key namespaces (`resonance_*` vs `feed_weight_*`) so tuning one never silently moves the other. **A migration must NOT `INSERT INTO platform_config`** — its INSERT never runs on a DB booted from `schema.sql`, so the dial is simply absent there (the drift guard's Check 4a header carries the mechanism and the measurement). Add the dial (value + description + the measured rationale) to `shared/src/db/config-defaults.sql`, which `migrate.ts` applies on **every** run with `ON CONFLICT (key) DO NOTHING` — so a missing default self-heals on the next ordinary migrate and an operator's tuned value is never overwritten. Corollary for **write** paths: never `UPDATE platform_config … WHERE key = …` (a bare UPDATE matches zero rows and reports no error when the key is absent — that is how `jetstream_healthy` silently never persisted); upsert. Runtime *state* that happens to live in this table (`payouts_halted`, whose absence means "not halted" and which is DELETEd to resume) is deliberately NOT in the defaults file. **A dial with no reader is not a dial** — seeding a key and typing it onto `PlatformConfig` buys nothing if every consumer still holds a literal, and the failure is silent in the worst way: the operator's UPDATE succeeds, reports nothing, and changes nothing (`free_allowance_pence` governed nothing at all until migration 169 — both account INSERTs, the column DEFAULT and every display carried their own `500`). When adding a dial, grep that the literal it replaces is *gone*. **The fix for a dead dial is always to give it a reader, never to drop the seed** — a key any migration has *ever* seeded cannot be un-seeded, because Check 4c replays every historical migration seed onto the defaulted DB and fails if a row appears; removing it from `config-defaults.sql` fails CI by construction (`publication_payout_threshold_pence` was dead from migration 038 to 2026-08-06, its cycle binding the *writer* dial, and "wire it or drop the seed" was never the choice it looked like). **And a dial whose default equals another dial's cannot be pinned by a test that seeds the defaults** — with both at 2000, a test passes against the crossed wire exactly as it passes against the fix, which is how that one survived every green suite for years; set the two to different values and assert which reached Postgres (`payment-service/tests/payout-threshold-dials.test.ts`). **And a dial's value at the moment of an irreversible event is stamped, never re-read** — where the dial sets what a user was granted, charged or promised, that figure is a historical fact about them and belongs in a column on their row (`accounts.free_allowance_granted_pence`); reading the *current* dial to display it restates history the next time an operator tunes it, telling a reader gifted £5 that they were gifted £7.50. The dial governs what happens NEXT; the row records what happened. **An in-code fallback is a SECOND copy of the dial, so it is parity-tested against the defaults file** — `shared/src/db/config-defaults-parse.ts::diffAgainstDefaults` is the one home, applied by the three parity suites (`shared` `loadConfig`'s nine money dials, `gateway` feed-rank, `feed-ingest` resonance; each drives the real loader against an empty table, so it pins the shipping fallback path rather than a copy of it, and greps the loader's source so a new dial cannot ship unchecked). A drifted fallback never errors — it substitutes silently, and it is invisible **exactly when the row is missing**, which is the one case the fallback exists for. CI-enforced by `scripts/check-schema-drift.sh` Checks 4a/4b/4c (no new migration seeds config · a fresh DB carries every dial · the defaults file covers every historical migration seed). Spec: `docs/adr/SOCIAL-PROOF-RESONANCE-ADR.md` D2/D4.
- **A dark-ship brake gates the narrowest shared choke point, not the renderer**: when a feature ships dark, put the flag at the single server-side point every read path already funnels through — for a display feature that is the shared projection/mapper (`RESONANCE_GLYPH_ENABLED` nulls `Post.resonanceBand` in `gateway/src/lib/post-mapper.ts`, so no band leaves the gateway and the glyph *cannot* render), not the component. One home means no `NEXT_PUBLIC_*` twin to flip in lockstep and no half-lit state where server and client disagree (the `PLEDGES_ENABLED` twin is the shape to avoid when a server-only gate would do; a twin is only forced when the web must change *layout*, not just omit data). Display-only brakes must not gate the write path — the scoring/ingest crons keep filling their columns while dark, so flipping the flag needs no backfill and is instantly reversible. Every brake gets a `DEPLOYMENT.md` row + a `docker-compose.yml` default, and if flipping it depends on evidence, the queue item records that evidence as the gate. Spec: `docs/adr/SOCIAL-PROOF-RESONANCE-ADR.md` step 4.
- **Compose surfaces**: exactly two for short-form — the global `ComposeOverlay` (`web/src/components/compose/ComposeOverlay.tsx`, mounted by `LayoutShell` for platform-mode routes with no pane open) and the workspace `Composer` (which the chromeless workspace bridges `useCompose.open()` into — see the no-topbar invariant). Do not add a third. Two modes (note/reply) via `web/src/stores/compose.ts`; renders through `<Glasshouse>`. Spec: `planning-archive/ALLHAUS-REDESIGN-SPEC.md` §3.
- **Article writing — one surface**: the full TipTap `ArticleEditor` (`web/src/components/editor/ArticleEditor.tsx`) is the single article editor. It renders two ways from the same component (`chrome` prop): the standalone `/write` page (`chrome='page'`, addressable for direct visits/bookmarks/deep-links) and the global **EditorOverlay** (`web/src/components/workspace/EditorOverlay.tsx`, `chrome='overlay'`, mounted unconditionally in `LayoutShell` like `ProfileOverlay`, chromeless). ### Three-voice typeface system

| Voice                     | Typeface      | Use for                                                                    |
| ------------------------- | ------------- | -------------------------------------------------------------------------- |
| **Literary** (serif)      | Literata      | Article prose, publication names, content previews, the reading experience |

### The ∀ mark — one canonical construction

**The ∀ renders in ONE form: the disc.** The bare crimson glyph was retired from the design language 2026-07-25 and its component (`web/src/components/icons/ForAllMark.tsx`) deleted along with every render site (Nav wordmark + canvas beam, Footer lockup, About divider, PaywallGate ornament, the end-of-article ornament in `ArticleReader`, and the auth / waitlist / tribute-claim confirmation cards) and the dead `.logo-spin` CSS. **Never reintroduce a bare ∀** — not as an ornament, a divider, a lockup partner, or an empty-state mark; where one stood, whitespace carries the break, and the wordmark stands as type alone. The disc form is the mark's sole rendered instance. Don't introduce a second construction or tweak one instance alone — geometry changes re-derive every instance from the spec. Typed ∀ characters (ForallCeremony's Literata glyph, "∀ Traffology", Explain copy) are a different register, exempt. Specs: `docs/adr/FORALL-CUT-AND-LOCKUP-ADR.md` §III.1 (the disc stance); `docs/adr/LOGO-REFINEMENT-SPEC.md` retains the bare stance's ~20.5° geometry as **spec only, with no implementation**.

- **Disc form — ≈16.7° splay, feet flush through the top rim and the mitred apex kissing the bottom.** The `ForallMenu` trigger's idle-∀ group, `ForallDisc`/`ForallLockup` (the landing lockup + coda), `favicon.svg` (whose rasters `icon-32.png`/`apple-touch-icon.png` are regenerated from the SVG, never edited directly), and the brand exports in `web/public/brand/`. The narrower splay is a **consequence** of pinning both ends to the rim — do not re-derive it from the bare stance's ~20.5°, which belonged to a mark with no rim to kiss. Canonical in a 200-unit frame (disc r=94 at (100,100)); the in-app 56-unit frame (disc r=28) is that scaled by 28/94 — legs `M14.36 1.61 L28 47.15 L41.64 1.61` w5.06, crossbar (19.96,20.26)→(36.04,20.26) w4.17, clip at the literal rim r=28 so the trim is flush (an inset clip leaves the ink slice the overshoot exists to avoid). The trigger and favicon were ported onto it 2026-07-22, closing the two-stance drift the ADR's honesty note recorded.

The disc form has two **realisations** of that one geometry — **painted** (glyph drawn over the opaque disc) and **cut** (the ∀ a real hole; brand exports in `web/public/brand/`, whose rim-kiss variant applies to exports only). Punch only where the ground is ours to show; every unpredictable ground (favicon, Stripe, OG composites) paints. **The workspace disc always paints; the cut realisation is exports-only.** The idle desktop disc was once a *live lens* — a punched white disc + wordmark composited `mix-blend-mode: difference` against the canvas — and the stacking-context choreography that kept it legible (`z-index: auto` on the lockup, `body { isolation }`, the canvas `isolation`, the `lensSuppress` registry) was load-bearing. **All of it is deleted** (WORKSPACE-COLUMN-LAYOUT-ADR §VI, Slice 4, 2026-07-22): the disc is docked in an opaque nav row, so there is nothing left to float over, and the viewport-sized blend surface re-rendered on every scroll frame is no longer paid for. Do not reintroduce a blend, a `body`/canvas `isolation` scope, or a suppression registry for one. Specs: `docs/adr/FORALL-CUT-AND-LOCKUP-ADR.md` (geometry + the lockup ratio, still current; its §IV lens is superseded), `docs/adr/WORKSPACE-COLUMN-LAYOUT-ADR.md` §VI.

### Use design tokens, not inline sizes

| Token          | Size                                  | Use for                                          |
| -------------- | ------------------------------------- | ------------------------------------------------ |
| `text-ui-xs`   | 13px sans                             | Small UI text, descriptions, secondary copy      |
| `text-ui-sm`   | 14px sans                             | Standard UI text, form values, list items        |
| `text-mono-xs` | 11px mono                             | Small mono data (dates, amounts, tabular values) |
| `.label-ui`    | 11px mono, uppercase, 0.06em tracking | All infrastructure labels and metadata tags      |

Never hand-roll `font-mono text-[12px] uppercase tracking-[0.06em]` — that is `.label-ui`. Never use `text-[13px] font-sans` — that is `text-ui-xs`. Never use `text-[14px] font-sans` — that is `text-ui-sm`.

**Global type size.** Settings exposes a per-device type-size control (`web/src/stores/typeScale.ts` + the headless `TypeScaleHydrator` mounted in `LayoutShell`; UI is `account/TypeSizeControl`) that scales the root `html` font-size. Because the tokens above are **rem-based**, they scale with it. Hardcoded `text-[Npx]` arbitrary values do **not** scale — one more reason to use the tokens. An arbitrary **rem** value (`text-[0.90625rem]`) does scale, so it's the correct escape hatch for a size with no token. The card chassis was migrated off px 2026-07-20: the byline already rode `.label-ui`, and the mono action/counter/origin/quote labels now use `text-mono-xs` (= the old 11px exactly) / `text-[0.625rem]`, with playscript dialogue at `text-[0.90625rem]` (= the old 14.5px) — all pixel-identical at the default root, and scaling above it. (Remaining gap, deliberate: the card **body** is sized by the per-feed text-size control as an inline px number (`ctx.bodyPx` ← `TEXT_SIZE_PX`), so it does not compound with the global scale. Making it rem would multiply two user-facing size controls — a design call, not a cleanup.)

Always use `.label-ui text-grey-400` for form labels. Not `text-ui-xs uppercase tracking-wider` or `text-sm text-grey-600`. **Exception — on the Glasshouse interior (`bg-glasshouse`, now white) and its `bg-glasshouse-well` (`#F5F4F0`) inset fields, labels are `.label-ui text-grey-600`**: `grey-400` is too weak on the wells, so labels there stay `grey-600` for one consistent treatment across pane and wells (see the Glasshouse exempt-surface rule).

### Buttons

Use the defined button classes: `.btn` (primary), `.btn-accent` (crimson), `.btn-ghost` (background), `.btn-soft` (secondary/soft). Do not hand-roll button styles inline.

**Focus state — `:focus-visible`, never bare `:focus`.** A focusable control must show its ring only for keyboard focus, via a `:focus-visible { outline: 2px solid var(--ah-crimson); outline-offset: 2px }` rule (the `.btn*`/`.focus-ring` classes already carry this; the 2px outlines are the a11y exemption to the no-hairline rule). A control that can't take a `.btn` class (e.g. the ∀ disc, `.forall-trigger`) needs its own class with that `:focus-visible` rule **plus** `:focus { outline: none }` to suppress the UA default — otherwise it re-trips the browser ring for mouse users on every programmatic refocus (`.focus()` after a menu closes). Never inline `outline: "none"` (it has higher specificity than the `:focus-visible` rule and kills the keyboard ring too); add `-webkit-tap-highlight-color: transparent` to kill the mobile tap-flash.

### Text-link actions

`.btn-text` for inline text-link actions (13px sans, black, medium). `.btn-text-muted` for secondary (grey, hover:black). `.btn-text-danger` for destructive (crimson). Do not hand-roll with `text-ui-xs text-black font-medium` or similar.

### The public register — every logged-out surface, one chassis

`web/src/components/public/` is the chassis for everything outside the workspace, and there is no second one (the black topbar is deleted — see the escape invariant). `usePublicPalette()` resolves `basic` against `useResolvedDark()`, so the register follows the global light/dark toggle; `PublicVessel` carries `LIGHT_ISLAND_STYLE` so its derived text ramps stay deterministic, `PublicNavRow` does **not** (it is global chrome on the plain `--ah-bone` floor and inverts with the toggle).

- **Two chassis, and the difference is whether it scrolls.** `PublicShell` is **fitted** — the vessel is wholly on screen and its *contents* scroll (`minHeight: 0` / `overflowY: auto`, with the interior `PAD` **on the scroll body** so the first card starts at the mouth and the last ends at the wall; padding on the frame leaves a dead band content slides under, which looks like a bug). A ⊔ whose closing wall is below the fold isn't a vessel, it's a left-and-right pair of rules. **Two bounds, both live: never taller than the viewport, never taller than its content.** Every link of the chain (shell measure column → frame → scroll body) is `flex: 0 1 auto` — no grow, so a short page's ⊔ is exactly as tall as what it holds and `.ah-public-fit` centres it on both axes; shrink kept, with `minHeight: 0`, so a long page still shrinks to the remainder and scrolls inside its walls. `flex: 1 1 0` anywhere in that chain re-stretches it and puts a frame round a great deal of nothing. `PublicPage` is the **scrolling** counterpart for the share/SEO surfaces, which have no vessel on purpose: they *are* the reading experience, and a frame round an article boxes the one thing the site exists to deliver. Measures: `prose` 720, `form` 480, no third. `dvh`, never `vh` — `100vh` is the *largest* mobile viewport, so a `vh`-fitted vessel hides its bottom wall behind the browser chrome.
- **Vessels are single-wall, and on a phone there is no vessel at all.** The doubled wall (wall / 8px buffer / wall) is `/`'s alone — an argument about the lattice, worth a frame's weight on the one page whose job is to state the house's terms, not worth it around a login form. **And it is `/`'s on DESKTOP alone**: at ≤767px every logged-out page drops its ⊔ entirely — `/` goes full-bleed (floor margin, outer wall, buffer and then the surviving single wall all gone; interior pad 16 → 8), and `PublicVessel` loses all three walls. The ⊔ says *this is one object among several*, true of a feed on a workspace floor and false of the only column on a phone screen, where it is ink framing the one thing already filling the viewport — the same call MOBILE-LAYOUT-ADR made when the mobile workspace dropped its vessel chassis outright. Both frames stay in the tree as plain flex columns so the components keep one shape. Geometry for both form factors lives in `globals.css` — `.ah-landing-area` / `.ah-landing-frame*` (§1c) and `.ah-public-vessel` (§1a-bis) — **never a `useIsMobile` branch**, since these pages are SSR'd and a JS breakpoint paints the walled chassis on a phone and snaps after hydration. Only the palette-derived wall colour crosses into the components, as `--ah-landing-wall` / `--ah-public-wall`; declaring a border inline would beat the media query and the walls would never drop.
- **A field is a card with a 4px slab under it, and focus is the slab going crimson** (`Field.tsx`). Nothing is boxed; the slab says "write here" the way a ruled line on paper does. **Every input is ≥16px** — below that iOS Safari zooms on focus and strands the fixed row mid-screen. **No spinner, no tick glyph, no `animate-pulse rounded` skeleton**: waiting is `IndeterminateSlab` (the 4px weight sweeping the field it already occupies, pinned full-width under `prefers-reduced-motion`), success is the word in the serif and the redirect. A skeleton is a guess about a layout rendered at the one moment you can't know it, and it ships a border-radius the house doesn't have.
- **Lines inside a card are `controlLine(palette)` (= `cardTitle`), never `palette.walls`.** `walls` is the vessel's *structure* and is meant to recede in dark — where it is `true-black` on an `ink-900` card, i.e. invisible. `controlLine` is byte-identical to `walls` in light, and islanded bone in dark; 4px of ink on white and 4px of bone on ink-900 are the same gesture. Scrollbars pass `--ah-scroll-thumb` = `cardMeta` (outside `DARK_SLUGS`, so one quiet grey in both modes).
- **A fitted public page's floor is `palette.interior`, not `var(--ah-bone)`.** Floor and interior must be the *same* colour — that is what makes the walls read as ink rules on a continuous ground rather than a box, and why content scrolling out of the open mouth vanishes instead of cutting against a seam. Bone delivers that in light but not in dark (bone → 20 19 17, interior stays ink-925's 26 26 24). **This diverges from the workspace on purpose**: there the floor *is* bone and interiors *are* ink-925, so feeds read as islands on a floor — right for a surface holding many feeds, wrong for a page holding one vessel pretending not to be one.
- **One accent per screen** (`.btn-accent`, only on the row's waiting-list CTA — a second primary action means the page is wrong, not the button) and **one ∀ per screen**, in the lockup, where it is also a link home.
- **A public surface shows the product as LIVE MARKUP, never a screengrab, and never with real people's content.** `/`'s showcase is three inert components (`web/src/components/landing/demos/`) reading the same palette tokens as the app, so they invert with the global toggle, re-proportion for mobile and cannot drift from a colour retune (the `.webp` captures they replaced showed the app's 15px type at ~5px). Rules, all of which have bitten:
  - **Register is CSS, not JS.** Each demo has ONE knob (a root `fontSize`, everything inside in `em`), and the knobs live in `globals.css` §1d beside the §1c geometry — an SSR'd page must not pick its register in JS. The one sanctioned departure from §1c's media-query rule is `CanvasDemo`'s container query (`clamp(8.5px, 1.95cqw, 12px)` off `container-type: inline-size`), safe for §1c's own reason: a container query is CSS, resolving at paint on SSR'd markup.
  - **A demo SCALES, it does not REFLOW, and it hides nothing.** `CanvasDemo`'s irregular four-feed arrangement *is* its argument (any size, any position, either orientation); tidying it into a regular stack at narrow widths would demonstrate the opposite of the claim.
  - **A demo of the workspace obeys the workspace's own rules** — getting them wrong is what makes a figure read as not-quite-the-product. The bar IS a vessel's bottom (never a bar *plus* a bottom wall); a horizontal feed is a ⊐ (top+right, open left), not a ⊔; interior padding is 2× the wall with the inter-card gap 1.5× (the floor's 8/16/12); the gutter between vessels equals the wall; and the arrangement must be a shape a stored column order can express — **columns of slots, never a band spanning under two columns** (which reads as a footer, not a feed).
  - **Vessels CLIP at a fixed height in `em`, and every feed is over-filled.** A vessel on the floor is a fixed rectangle whose cards scroll; since two columns are always equally tall, a content-sized one opens an untunable void inside whichever feed holds less. `em` not `aspect-ratio` (past the clamp's floor a ratio-derived box keeps shrinking while its `em` cards do not, and the feeds close over their own content), and the height is a ceiling too — the figure must fit the landing vessel's scroll area or the arrangement can never be seen whole.
  - **`DemoVessel` has two geometry modes, and omitting `wall` with no matching §1d rule renders a wall-less vessel silently** — a demo whose walls scale in `em` cannot set them inline, because an inline zeroed border beats `@layer components`.
  - **The cards are a deliberate COPY of the card grammar, not a reuse of `PostCard`** (which would drag the whole post stack onto the page a stranger loads cold) — so re-read them against `Byline.tsx`/`PostOriginTag.tsx`/`QuotedEmbed.tsx` when the real card changes.
  - **Demo content — bylines, publications, handles, bodies — is invented, and a photograph is DRAWN.** A real person's post retyped as markup on a page that sells something is indistinguishable from words we put in their mouth, and a stock photograph is a real place someone owns. `DemoPhoto` builds its picture from canonical **neutral** slugs (`grey-200 → grey-300 → stone-400 → wall-grey → ink-925`), so it needs no raw hex and — correctly — never inverts with the mode (a feed's surface follows the toggle; a photograph in it does not). Protocol labels (`via RSS`/`via Bluesky`/`via Nostr`) are the exception and must stay literally true, being the claim. **"Invented" is not enough for a HANDLE**: a handle lives in a live registry, so an invented one resolves to whoever holds it (an invented `.bsky.social` handle shipped 2026-07-29 belonged to a real account, under an invented corruption accusation). Any demo identifier that resolves — handle, NIP-05, email — lives only in a namespace the operator controls (`all.haus`), verified against its real registry before shipping (mechanism note: `CanvasDemo.tsx`) — **and then verified in the SERVED BYTES**, because a CDN edits markup: Cloudflare's email obfuscation rewrites anything email-shaped, NIP-05 *is* email-shaped, and the Nostr demo shipped to production reading `[email protected]` with both earlier clauses satisfied (`curl` the page; `DEPLOYMENT.md` › *Known limitations*).
  - **One story crosses the demos as a SPINE, not as the world.** A canvas of things nobody would click argues against the page's own claim, and a gate closing over a gentle reminiscence never shows anyone would pay to pass it — but a wire of leak-burial-collapse in every card fails it the other way, since a reader who only wanted the grim column would not need four feeds. So the story appears at five spine points only; roughly a third of the cards are light, held to the same standard (delight is a beat, whimsy is the parish magazine); the reader demo's blurred floor deliberately carries none of it; the reader's gated piece and the omnivore's paid card are ONE article (retitle both or neither); and no other post repeats across the three files. The current world and its five points: LOGGED-OUT-REGISTER-ADR §IX 7septies/7octies.
  - **Check any patch to this page against this rule and `check-hairlines.sh` before reading it for design — and RENDER it.** Two successive patch bundles arrived with real names in them and a `height: 1` divider, and a browser found four chassis defects here that compiling, linting and reading did not (ADR §IX *Still open* 7).

Spec: `docs/adr/LOGGED-OUT-REGISTER-ADR.md` — §IX is the as-built record (where the code and the plan diverge, and what is still open). Read it before touching the register.

### Colour values — canonical registry, never a raw hex

Every colour the frontend renders lives as a CSS-variable pair on `:root` — `--ah-<slug>` (colour) + `--ah-<slug>-rgb` (RGB triple) — defined in `web/src/app/globals.css` from the ordered canonical registry `web/src/lib/palette/registry.ts` (keep both in sync, same order; the registry header documents the contract). Never introduce a raw hex/`rgb()` literal in web code: inline styles reference `var(--ah-<slug>)`, Tailwind colour tokens already resolve to the triples (alpha modifiers like `bg-white/40` keep working), and translucent washes are `rgb(var(--ah-<slug>-rgb) / 0.x)`. A genuinely new colour gets a registry entry + `:root` pair first. Contexts that cannot resolve `var()`: SVG presentation attributes (set `style={{ fill/stroke }}` instead) and canvas (read the triple off `getComputedStyle(document.documentElement)` at draw time — see `ProvenanceBar`). Exempt, deliberately hard-coded: Stripe iframe appearance (`CardSetup.tsx`), brand-locked SVGs (Google logo), print CSS. The Palette devtool — `web/src/components/devtools/PalettePanel.tsx` + `web/src/stores/paletteDevtool.ts` — live-tunes the registry vars (overrides persist in `localStorage` `ah:palette-overrides`). **Operator-only, not user-facing** (GLASSHOUSE-AND-PALETTE-ADR §III.5): the ForallMenu "Palette" row and the Settings preset-theme picker (`ThemeSection`, now parked) were retired to reclaim a single canonical identity, and existing user overrides are purged once on upgrade (headless, sentinel `ah:palette-purged-v1`). The panel is reached via `?palette` or the `Ctrl+Alt+P` chord. **Do not delete** — it remains the operator tuning surface behind the per-feed colour schemes (history: `planning-archive/feature-debt.md` §3; the live residue — free colour wheel + per-scheme accent — is CONSOLIDATED-TODO §9), and boot-time hydration of any persisted overrides now lives in the headless `PaletteHydrator` (`web/src/components/devtools/PaletteHydrator.tsx`, mounted at the app root) — *that* component is the load-bearing mechanism; never remove it. Per-feed colour **schemes** are a separate axis (`feeds.appearance` / the layout store, `components/workspace/tokens.ts` `PALETTES`), not the override store, and are untouched by the purge. The Glasshouse pane, ∀ chrome (`ink-925`) and trust-pip slugs stay locked out of any theming (`THEME_LOCKED_SLUGS`). The registry + var indirection itself is permanent.

### Workspace colour schemes — colour from the palette, never hard-code

Per-feed colour **schemes** in `web/src/components/workspace/tokens.ts`. **A scheme is a COLOURWAY (seasonal character — hue / energy / warmth), ORTHOGONAL to light/dark**: the colourway is per-feed, but whether it renders light or dark follows the **global** light/dark toggle (`useColorScheme`). Five colourways: `basic` plus four curated surface families (`spring`/`summer`/`autumn`/`winter` — one shared grammar of saturated frame → tinted ground → clean reading surface, DESIGN-TUNING-FINDINGS §3 superseding the Brazilian-modernist `anil`/`vela`/`caju`). **Dark variants must cohere as a SET, not each on its own** — a workspace shows several feeds at once, so the dark `interior`+`card` are a near-shared dark neutral (only faintly hue-tinted) and identity rides the `walls`/bar spine: four clean chromatic hues at matched luminance (~0.38), the Claude-Code "bright accents on a shared dark ground" lesson (DESIGN-TUNING-FINDINGS §3 addendum, re-tuned 2026-06-22, superseding the earlier contrasting-accent-ground grammar that fought across side-by-side feeds). **Each colourway carries BOTH a light and a dark surface set** (registry slugs; the opposite-of-original variant has a `-dk`/`-lt` suffix — Spring/Summer/Autumn authored light-first, Winter dark-first), and `basic` is the two hand-tuned reference palettes `BASIC_LIGHT`/`BASIC_DARK`. They carry **no user-facing display name** — the `SchemeDot` (a single dot in the scheme's forceful `walls` colour, previewing the variant for the *current* global mode) is the sole identifier, so the FeedComposer `Colour` control shows no text indicator. **`paletteFor(scheme, dark)`** takes the resolved global-dark flag and returns a `VesselPalette` (`cardBg`/`cardTitle`/`cardMeta`/`interior`/`barText`/… + `isDark`) for that colourway's light or dark variant — every field a `var(--ah-…)` reference into the canonical registry; the eight seasonal variants are precomputed (`SEASONAL_PALETTES`). **Quoted-post embeds ride the `walls` surface, not `interior`** — `quoteBg`/`quoteText`/`quoteMeta` are derived against walls luminance (Addendum B), so a quote reads as a recessed frame, not a second content well. A curated colourway-variant defines **surfaces only** (walls/interior/card registry slugs); every text colour is **derived by luminance** (`deriveVesselPalette`) between the two reference text ramps, with the semantic flip riding the same switch (crimson → crimson-soft on dark cards) — never hand-set a text colour in a scheme, and curate **each variant's** card surface clearly light or clearly dark (mid-luminance defeats both ramps). The scheme is **feed character**: persisted server-side (`feeds.appearance.scheme`, migration 112; picked from the FeedComposer `Colour` menu — `SchemeMenu`, a little palette of one `SchemeDot` per scheme — GLASSHOUSE-AND-PALETTE-ADR §III.4), mirrored into the layout store's legacy `brightness` field as the per-device cache/fallback. The colourway id list must mirror `FEED_SCHEME_IDS` in `gateway/src/routes/feeds/crud.ts`; retired ids (incl. the former mode-fixed `primary`/`dark` → `basic`) are migrated on read by `normalizeBrightness`'s alias map (`SCHEME_ALIASES`), so renaming schemes needs no DB backfill. **Density rides the same model** (`feeds.appearance.density`, no DDL; the gateway's `FEED_DENSITIES` is a deliberate **superset** of the `Density` type in `tokens.ts` — a three-state cycle **Standard → Condensed → Headline** (the retired-but-still-accepted `'full'` aliases to `'standard'` so a stale client's round-trip doesn't 400; the web normalises unknown/retired densities to `'standard'` on read). Condensed tightens padding and hides media + the action row (standfirst kept); **Headline** (added 2026-07-25) does all that **and drops the standfirst/dek** — a feed reads as source + title only (implemented by forcing the card's body to `one-line` mode in `PostCard` when density is `headline`; notes/external clamp to a single line). Don't "fix" the superset mismatch by re-mirroring; a *new* density still gets added to both `FEED_DENSITIES` and the `Density` type), as do `feeds.hidden` + `feeds.sort_rank` (migration 113): hide and rank are feed character, never per-device layout state, and the numeral is derived 1..N over **visible** feeds in `sort_rank` order — one rule on every surface (MOBILE-LAYOUT-ADR §V/§VII).

### Desktop workspace floor — columnar, derived, taut

Spec: `docs/adr/WORKSPACE-COLUMN-LAYOUT-ADR.md` (accepted and **fully shipped 2026-07-22**, Slices 0–5 — virtualization, the pure layout module, the store, the floor, the nav row, the regimented hotkey; check §X's as-built notes before touching workspace layout). This section **supersedes** the free-coordinate floor (signed store coordinates, `computeExtent`'s signed origin, mover-yields collision, the bootstrap heal) — that model, and every rule that defended it, is retired.

**Geometry is DERIVED, never stored.** What persists is an **order** — `{columns: [{id, slots: [{feedId, w, h}]}]}`, left to right, top to bottom — plus per-slot sizes; `h: null` means "fill the column's remaining share". One pure function, `deriveGeometry(layout, {w, h, navRowH})` in `web/src/lib/workspace/layout.ts`, turns that into final canvas rects, per-column spans and a `floorWidth`. **A state that violates the spacing rules is unrepresentable**, so there is nothing to detect, resolve or heal — no `findRestingPosition`, no `clampSizeClear`, no `repairRestingLayout`, no resting-overlap heal, and no `settleAfterAbandonedMerge`. Never reintroduce a stored pixel position, a second coordinate space, or a resolver that repairs one. Put new geometry in `layout.ts`, which is property-tested (`layout.test.ts`, 47 tests: no rect overlaps, every gutter exactly `GRID`, `floorWidth` taut, every pointer resolves to a legal `Drop`).

- **The floor is finite and taut, and the stripe is the unit.** Columns start one `GRID` from the left edge, each subsequent one `GRID` past the previous column's bounding right edge (= its widest slot); `floorWidth` is the last right edge + `GRID`. `GRID = WALL = 8`, so a gutter between adjacent vessels reads as three even bands — wall / buffer / wall. A strip narrower than the viewport **centres** (`offsetX`, baked into the rects); past that it left-aligns and scrolls. Dragging cannot create empty space and hiding cannot leave holes, so there is no Excel-style lost scrolling. Ctrl+←/→ still jumps to the far ends (guarded: not in editable fields, not with another modifier, not while a Glasshouse is open, not mid-drag).
- **`deriveGeometry`'s rects are FINAL canvas coordinates** — centring already applied. That is the *one* conversion seam: the `Vessel`'s `position`/`size` props take them verbatim and consumers convert nowhere else. **Degradation is derivation's job**: a shrunken viewport (window resize, or Slice 4 subtracting the nav row) compresses `null` slots toward `SLOT_MIN_H` first, then squeezes fixed heights proportionally — the *stored* layout is never rewritten by a resize, so growing the window restores what shrinking it hid.
- **Drops resolve to slots, not coordinates.** A drag **holds its slot open** for the whole gesture — nothing is spliced until release, because collapsing live would shrink `floorWidth`, the browser would clamp `scrollLeft`, and the floor would slide under the pointer. The vessel hands back **only the pointer**; §IV.2 splits each rect by zone — an outer `EDGE_BAND` adjacent to a column or stack boundary resolves to **insertion** there (a `GRID`-wide crimson stripe previews the gutter that would open), the **central region** arms a **merge**. Hit-test the **slot's own rect**, never the column span (the empty band beside a narrower slot must not arm a merge from visually empty ground), and **capacity-gate** the vertical bands for cross-column drops — the floor has no vertical scroll, so an over-stacked column pushes feeds below the nav row, unreachable. A drop that resolves structurally unchanged (back into its own held-open slot) is a **no-op and commits nothing** (`dropIsNoop` — load-bearing under the regimented mode, below). Every pointer position maps to some legal drop, so "drag as far as you like" is safe; holding near a viewport edge **auto-pans**, compensated against framer's own drag origin so the vessel stays under the cursor — the only way a gesture reaches an off-screen column on a floor with no slack.
- **A declined merge needs no placement at all.** The source never left the layout, so dismissing `MergeFeedConfirm` just clears `pendingMerge` and the vessel springs back to its held-open slot; the target never moves. Never reintroduce a cancel-path settle.
- **Resize clamps against the column, and displaces nothing.** Width is free to the envelope max — growing a slot widens its column and the columns to the right slide by recomputation; height stops at the stack remainder (`clampSlotSize`, applied per frame so the handle visibly stops where the commit would). The live proposal feeds back through derivation, so those columns slide *with* the handle rather than jumping on release. **Resize has the drag gesture's edge auto-pan too** (`startResizePan`): the taut floor has no slack to the RIGHT of the last feed, so widening the rightmost vessel used to stall at the viewport edge. Holding the handle near the right edge now GROWS the slot continuously and scrolls the floor to keep the handle under the cursor — pushing a feed into new workspace width is as easy at the right end as in the middle. The loop starts on the first real move, never a bare click.
- **Every write path goes through the layout module.** Hide/delete/merge-away → `removeFeed` (splice the slot, drop an emptied column, recomputation compacts); unhide/new feed/adopt → `insertFeed` (append a right-most column at `FACTORY_W × null`); bootstrap → `reconcileFeeds(liveIds, visibleIds)`, which prunes slots the server no longer returns *or* has hidden and places every visible feed that has none — that same call is the first-run path (one column per seeded starter feed, list order). Feed numerals (`sort_rank`) are independent of layout: there is no requirement that Feed 1 be left-most.
- **`\` is the regimented view, and a view is not an edit** (§V). Plain backslash toggles the parade ground: every visible feed on screen at once, one column each, numeral order, factory width scaled down uniformly to fit (floored at `REGIMENTED_MIN_W`, a deliberately generous readable minimum wider than `SLOT_MIN_W` — the parade is an overview, not a cram-onto-one-screen; below it the floor admits horizontal scroll). It **derives** a transient layout from the feed list — the stored layout and the v2 key are untouched, which is what makes leaving it free and crash-safe; there is no snapshot to lose, **so never add one**. It is ordered by the **numeral**, not the raw server rank, so the columns always match the numerals painted on the vessels. Gestures stay live: a layout **mutation** (a committed drop, a resize commit) calls `materializeRegimented` to stamp the parade as the custom layout, applies the one edit, and leaves the mode — but a **no-op drop is not a mutation** (a never-mind release back into the held-open slot must not stamp the parade over the custom layout; that was the silent-loss bug), **neither is a no-op resize** (a zero-movement press or cancelled gesture commits nothing, and `\` itself is refused mid-resize, mirroring mid-drag), and **feed-list changes are not layout edits** (merge/hide/delete/adopt apply to the stored layout and the parade re-derives; appearance changes apply in place). Anything reading the layout mid-gesture must read the *derivation the floor is arranged by* (`baseLayout`), never `useWorkspace.getState().layout` — under the mode that is the hidden custom layout. Guarded like every global binding here: no modifiers, not in an editable field, not while a Glasshouse pane / lightbox / editor overlay / local transient surface / Explain program owns the keyboard, not mid-drag. Persisted as the bare boolean `workspace:regimented:{userId}`.
- **Persistence is `workspace:layout:v2:{userId}`** holding `{columns, appearance}`, debounced 200ms (`web/src/stores/workspace.ts`, unit-tested in `workspace.test.ts`). **Layout and appearance are disjoint records** — layout purely structural, `appearance` purely per-feed (brightness/density/orientation/textSize), neither reaching into the other; scheme and density stay server-authoritative feed character with this record as their cache. The v1 key is read once at hydrate for the appearance fields (`textSize`/`orientation` are local-only, so a wholesale wipe would lose real settings), coordinates discarded, key deleted.
- **What is off-screen costs nothing** (§VII). A vessel whose derived rect falls outside the visible band (viewport ± one viewport width off `scrollLeft`, 200px dead band for hysteresis) is **parked**: chassis, numeral and bar stay mounted — it remains a merge target and an explainable root — while its card tree unmounts and the interior renders a flat wash (`contentsMounted` on `Vessel`). Per-feed data (`VesselState`: items, cursor, caught-up watermark) lives in the host, never in the unmounted tree — never move it into the vessel. The vessel instance survives, so it keeps its scroll body's `scrollTop`. Mobile is out of scope (the pager already bounds the mounted set to one page).
- **The ∀ lives in a fixed bottom nav row, and the floor ends above it.** `web/src/components/workspace/NavRow.tsx` (`NAV_ROW_H = 56`) is chrome only — full-width, `position: fixed` at the bottom, neutral `bone` ground that inverts with `html.dark` (global chrome, never a feed island), and **no divider**: it shipped with a 4px slab on its top edge and the slab was removed 2026-07-22 — the lockup docked at the row's right end is indicator enough, and a full-width rule across the viewport is a heavier statement than the row is making. The `NavRow` element itself stays a silent, empty reserved band; don't reinstate the slab (nor anything thinner — the no-hairline rule stands regardless). Its **centre now carries the muster** — a centred run of numbered feed roundels reporting each live feed's in-view / panned-off / minimised state and navigating to it (go-to-feed closes any open pane first), mounted as a **separate fixed layer beside `NavRow`** (state locality: geometry/pan/feeds live in `WorkspaceView`), not as a child of it, so the row keeps its `aria-hidden` and the muster owns its own `role="group"`. Numerals are stable identity over the live set. Spec: `docs/adr/NAV-ROW-MUSTER-ADR.md` (stable numerals §III, the muster §IV, polish §VIII.3; Phase 4 arrival flags deferred to their own ADR). The lockup (wordmark + ∀ disc, adjacent, reading as one mark) docks into its right end via `ForallMenu anchor="row"` — **one fixed container, the wordmark now a child of it**, since its separate fixed layer existed only so the deleted lens could blend. **The row sits above the Glasshouse band, mirroring the mobile bar**, so navigation stays live over any open pane (*Stacking order*); Glasshouse desktop placement subtracts `NAV_ROW_H` (`usePanePlacement`'s `usableH`, the mirror of its mobile `MOBILE_BAR_H` branch). **The one exception is the reader** (`coverNavRow`): rather than raise it above the row, `WorkspaceView` **un-mounts the row + muster while the reader is open** (`!readerOpen` gates both) and the reader's `usableH` becomes the whole viewport — so an immersive reading pane covers the toolbar region entirely and only the ∀ lockup floats over it. Every *other* pane keeps the row live; this is the reader's alone. Derivation reserves the space (`deriveGeometry`'s `navRowH`), so a vessel can never extend behind or below the row. Mobile has no such row: its bar is top-anchored, a deliberate one-rule-per-form-factor asymmetry.
- **The floor pans by native scroll, never a CSS transform.** A transform on the floor establishes a containing block and captures the `position: fixed` ∀ chrome and mobile bar, dragging them around with the canvas instead of leaving them pinned. The scrollbar is suppressed with `.scroll-silent` (a native one draws a banned single-pixel rule across the viewport). **A horizontal feed owns the sideways axis inside its walls and the chain stops there** (`overscroll-behavior-x: contain` on the ⊐ vessel's scroll body): left to chain, one swipe meant three things in sequence — scroll the feed, pan the floor, then the browser's back/forward gesture — selected by scroll state the user cannot see, and the third read as the workspace navigating away at random. Pan the floor from the floor, the muster, or Ctrl+←/→. **`overscroll-behavior` is only honoured on an element that is ACTUALLY scrollable**, so the floor's own `contain` is inert whenever the taut floor is narrower than the viewport (two or three feeds on a wide screen); `Floor` therefore also pins `overscroll-behavior-x: none` on `<html>` while the workspace is mounted and restores it on unmount — the workspace never scrolls the document sideways, so a horizontal document overscroll there can only be the nav gesture, but the rest of the site keeps it.

### Mobile workspace (one feed per screen)

At ≤767px (`useIsMobile`) the workspace swaps the canvas for `web/src/components/workspace/MobileWorkspace.tsx`: thin bar (wordmark · pip indicator strip · ∀ docked via `ForallMenu anchor="bar"`) over one full-bleed feed, paged horizontally in rank order. The canvas affordances (position/resize/orientation/merge) do not exist there; Glasshouse overlays render as full-screen sheets (presentation only). The pager claims a touch only when decisively horizontal, never from inside a horizontally-scrollable element or the pip (`[data-pip-trigger]` wins); resume keys off feed `id`, never the numeral. Both surfaces render cards through the single `WorkspaceView.renderFeedContents` path — don't fork it. **The bar is persistent chrome — `position: fixed` above every Glasshouse pane and below the ∀ disc** (*Stacking order*) — so it stays in place across all mobile views (over any open sheet, at any scroll position); mobile full-screen sheets inset below it (`usePanePlacement` `fullScreen` → `y = MOBILE_BAR_H`, `height = vh − MOBILE_BAR_H`). **The pip strip runs Feed 1 leftmost, in rank order — the same sequence as the desktop numerals** (`visibleSorted` passed directly at the call site; the 2026-07-04 `.reverse()` did the opposite of its stated intent and was removed 2026-07-06 — see MOBILE-LAYOUT-ADR §X's correction note), so the pip's positional aria-label always matches the FeedComposer title tapping it opens. Spec: `docs/adr/MOBILE-LAYOUT-ADR.md` (§X).

- **Any component inside a themed vessel interior or card takes the palette** (`palette: VesselPalette` prop, or `paletteFor(brightness)`) and colours every text/background — **including hover and active states** — from it. Never hard-code `text-black`/`text-white`/`bg-white`/inline `color` on an interior surface; it won't invert. Drive emphasis from a palette field (hover → `palette.cardTitle`) or a mode-agnostic affordance (`hover:opacity-70`); pick translucent washes via `isDarkPalette(palette)`.
- **Greys `500`/`700`/`800`/`900` are not defined** in `web/tailwind.config.js` (only `100/200/300/400/600`) — they emit no rule and silently inherit (dark-on-dark). Use a palette field, never an undefined grey.
- **Exempt:** "always-light" surfaces (the Glasshouse pane, fixed `bg-glasshouse` — `#FFFFFF` in light mode, the lightest/outermost layer, separated from the ground by the scrim and an elevation shadow, not by being a darker slab; + overlay panels with fixed light `panelBg`) never consume per-feed `PALETTES`. They are **mode-neutral, not literally light**: their surfaces/text are the neutral palette slugs (`bg-glasshouse`/`bg-glasshouse-well`/`bg-white`/`text-black`/`text-grey-600`), which **invert under the global dark mode** (see *Global light/dark mode* below) — so "keep their text dark" means *use the neutral var-backed tokens*, which read dark on light and light on dark, never per-feed palette fields or raw hex. Two fixed conventions on this interior:
  - **Text fields are the inset well `bg-glasshouse-well` (`#F5F4F0`).** The lightest layer is the pane (white), so a field reads as a well sitting a touch *darker* inside it — the inverse of the old model (field = bright white well on a parchment pane), flipped 2026-06-14 so the lightest colour is outermost. One treatment everywhere a text-entry field is defined against a modal interior (article editor title/standfirst/tags, composers, messages, …). Don't introduce a second field colour (`bg-grey-100`/`bg-white`/transparent) for an input on the pane. Container panels that merely *group* controls (cover/settings cards) stay a softer `bg-glasshouse-well/40` wash; the entry fields themselves are the solid well. (The standalone `/write` editor carries its own `bg-glasshouse` surface so the same wells read there too.) Floating material that is itself the outermost layer — dropdowns, popovers, the byline `AuthorModal`, the reader canvas — stays white (`bg-white`/`bg-glasshouse`), never a well.
  - **Secondary text is `text-grey-600` or darker.** Use black for primary, `grey-600` for secondary/labels across both the white pane and the `#F5F4F0` wells (one treatment); keep `grey-300` only for placeholders *inside* the well fields. `grey-400` is too weak on the `#F5F4F0` wells — don't use it for content there.
  - **A component that renders on *both* the fixed-light pane and the palette vessel must be palette-aware, not flat `grey-600`.** The fixed pane (now white `#FFFFFF`, light-only) and the themed vessel interior (`PALETTES`, light *or* dark) are two different contrast regimes: `grey-600` is correct on the pane but fails on a dark card. So don't "fix the pane" by hard-coding `grey-600` into a shared card/action component — drive its muted text from `palette.cardMeta`. Flat-darkening such a component is a dark-mode regression. Reference implementations: `VoteControls` takes an optional `palette?` and derives muted/active colour from `palette.cardMeta`/`palette.crimson`, defaulting to `grey-600`/crimson when omitted (so `PostActions` passes the vessel palette while the legacy fixed-light cards pass nothing); `PostThread`'s thread-nav greys read `ctx.palette.cardMeta`. Hover is the mode-agnostic `hover:opacity-*` fade, never a `hover:text-black`/`hover:bg-grey-100` that assumes a light ground.

### Global light/dark mode (per-device theme)

A sitewide **Light / Dark / System** appearance toggle, per-device (localStorage `ah:color-mode`, default `light`), modelled on the type-size control: store `web/src/stores/colorScheme.ts`, headless `ColorSchemeHydrator` (mounted in `LayoutShell`), settings UI `account/ColorModeControl`, plus a blocking inline script in `app/layout.tsx` (no white flash). It toggles `html.dark`.

**Mechanism — invert-at-root + feed "light islands":**
- Dark mode is an `html.dark { … }` block in `globals.css` that **inverts the canonical NEUTRAL ramp** at the document root (re-declares the `-rgb` triples). Because all global chrome reads those vars, the whole shell flips automatically: workspace ground, reader/profile/source/tag surfaces, **every Glasshouse overlay** (settings/dashboard/messages/admin), dropdowns/popovers. Only neutral chrome slugs flip (`DARK_SLUGS` in `web/src/lib/palette/island.ts`: `ink`, the greys, `white`, `glasshouse`, `glasshouse-well`, `bone`/`bone-bright`, `off-white`, `cream*`, `nav-grey`). Accent (`crimson*`), semantic (`trust-*`, `danger`/`vouch`, `klein-blue`), already-dark (`true-black`, `ink-925/900/850`, `stone-*`, `wall-grey`) and every per-feed season slug are **never inverted**.
- **Desktop feed vessels render their colourway in the global mode's light/dark variant** (the scheme is character, light/dark is global — see *Workspace colour schemes*): each `Vessel` reads `useColorScheme().dark` and calls `paletteFor(brightness, dark)`. The vessel **still** carries `LIGHT_ISLAND_STYLE` — but now the island's job is only to keep the *neutral text slugs* the derivation references (bone/ink/white/stone/…) resolving canonical regardless of mode, so the derived ramps stay deterministic; the **variant** (not the island) supplies the light/dark. Season surface slugs (`spring-*`/`winter-*`/…) are NOT in `DARK_SLUGS`, so they never invert — the variant choice is the only thing that flips them. (Profile/source/tag content carries no colourway and uses `globalContentPalette(dark)` OUTSIDE any island, relying on the html.dark inversion; **mobile feeds DO carry the colourway** and are islanded like desktop vessels — see below.) The **ForallMenu disc + dropdown** also carries the island (locked nav chrome: the dropdown stays light; the wordmark, a sibling over the floor, flips via `var(--ah-ink)`) and the FeedComposer **scheme swatch** (which previews the colourway's variant for the *current* global mode via `paletteFor(scheme, dark)`; the island only keeps `basic`'s neutral slugs clean in the preview). **The disc itself deliberately inverts under dark mode** — it stays islanded (tokens resolve to canonical light) but explicitly swaps to a light `bone` fill + dark `ink-925` glyph (`discBg`/`discGlyph` in `ForallMenu.tsx`, gated on `useColorScheme().dark`), the photo-negative of the light-mode dark disc; the dropdown is unaffected. Keep `DARK_SLUGS` in sync with the `html.dark` block. **`LIGHT_ISLAND_STYLE` must redeclare BOTH `--ah-<slug>` and `--ah-<slug>-rgb` for every slug** — the colour var is declared at `:root` as `rgb(var(--ah-<slug>-rgb))` and resolved *there* (where `html.dark` set the dark triple), so re-pinning only the `-rgb` triple on a descendant does **not** change the inherited resolved `--ah-<slug>` (the dark-on-dark feed + dark-disc-glyph bug, fixed 2026-06-21). Pin the colour var for `var(--ah-<slug>)` consumers and the triple for `rgb(var(--ah-<slug>-rgb) / α)` alpha consumers.
- **Mobile feeds render the per-feed colourway in the global mode's variant**, same as desktop: `WorkspaceView.renderFeedContents` uses `paletteFor(brightness, dark)` for both surfaces, and the mobile per-feed pages carry `LIGHT_ISLAND_STYLE` (`MobileWorkspace.tsx`) so the derived text resolves canonical. The mobile **bar** above the pages is NOT islanded — it is global chrome and inverts with the toggle.
- **Content that should follow the global theme** (profile/source/tag content-log cards) uses `globalContentPalette(dark)` from `tokens.ts` (the `BASIC_LIGHT` palette, whose slug refs invert, with `isDark`/crimson **plus the mode-specific stone tones** corrected for dark — `cardStandfirst`→`stone-300`, `nameLabel`→`stone-350`, because `stone-*` is **not** in `DARK_SLUGS` so it never inverts, and the light-mode `stone-600` would otherwise render dark-on-dark) — *outside* any island, so the inversion takes effect. Article prose (`prose`) gets a `html.dark .prose` `--tw-prose-*` override so the body/lists/rules invert too.

- **A surface that picks its palette variant in JS (islanded, SSR'd) must read the mode via `useResolvedDark()`, never the store's `dark` field.** The store's `dark` defaults to `false` and only flips once `hydrate()` runs in a post-mount effect, so `useColorScheme(s => s.dark)` reports light on the first client render. That is fine for CSS-driven chrome (the pre-paint `html.dark` script + the var inversion already handle it) but wrong for an islanded, inline-style-driven surface that resolves `paletteFor(scheme, dark)` in JS — a dark-mode visitor paints the light variant, then snaps to dark. `useResolvedDark()` (`stores/colorScheme.ts`) is a `useSyncExternalStore` reading the DOM `html.dark` class the blocking script set (client snapshot) with `false` as the server snapshot, so React reconciles it during hydration **before paint** — no flash. The islanded, SSR'd landing surfaces use it (`LandingVessel`/`ForallLockup`); the workspace `Vessel` reads `useColorScheme().dark` because it is client-booted behind a shell, not SSR'd on the first public paint, so its post-hydrate flip is never visible.

When adding a surface, decide: is it **global chrome** (let it invert — do nothing) or a **feed vessel** (island it)? Never island a profile/reader/overlay surface (it would stay light in dark mode). Spec: `docs/adr/GLASSHOUSE-AND-PALETTE-ADR.md` (global theme section).

Every fixed layer, low to high. **This table is the only place these numbers live** — state a rule where it belongs and cite the layer by name; never restate its z.

### Glasshouse (frosted workspace overlay)

Every surface that opens **over the workspace** (reader, messages, dashboard, composer, feed-settings, compose overlay, …) uses the canonical `<Glasshouse>` primitive (`web/src/components/workspace/Glasshouse.tsx`) — never a hand-rolled frosted scrim + centred pane. It owns the chrome: frosted scrim (`.gh-scrim` — backdrop blur **plus** a desaturate + neutral wash converging any per-feed scheme behind toward the mode's ground, so **separation is the scrim's job, identity is the pane's**; click-to-close), white pane (`bg-glasshouse` `#FFFFFF`, *lighter* than both the bone floor and the washed scrim ground, so it reads as lifted paper; its inset fields/wells are `bg-glasshouse-well` `#F5F4F0`, a touch darker, so the lightest layer is outermost; lifted by an elevation shadow alone, no top edge), Escape-close, body scroll-lock. Mount conditionally; pass `onClose` + `maxWidth` (+ optional `ariaLabel`, `persistKey`, `resizable`, `frameColor`, `fillHeight`, `coverNavRow`, `topSeam`); the caller's store layers on URL-sync. Mechanism: GLASSHOUSE-AND-PALETTE-ADR §III.3 (frame, ears, drag) and §III.6 (scroll, sizing, seam, `\`).

- **Feed-launched frame** — a reader/profile opened from a feed card frames itself in that feed's identity: pass `frameColor={palette.walls}` and the pane draws an **inverted, thinner echo of that feed's vessel** (⊓, open at the bottom — the inversion of the vessel's ⊔) as a pointer-events-none overlay in the content's padding gutters, disturbing no width or scroll. Only genuinely feed-launched call sites set it; feed-agnostic ones leave it null. **Not on the mobile full-screen sheet** — a full-bleed sheet has no gutter to carry it.
- **Skip ears, and their keyboard and touch twins** (reader only, feed-launched): half-circle ears protruding from the pane's left/right edges step the launching feed's **article list** in place — left ◀ previous, right ▶ next — dimmed when a step is unavailable. **←/→** is the keyboard twin (ignored in fields / with modifiers); **↑/↓** scroll the reading pane (active whenever the reader is open, not only feed-launched); on **mobile a horizontal swipe** across the reading pane is the touch twin, with the mobile pager's restraint (vertical-dominant gestures, and swipes begun inside a horizontally-scrollable child, fall through to scrolling). Ears are suppressed on the mobile sheet, where the reader's horizontal padding is instead responsive so the text column fills the viewport.
- **The pane is draggable, not fixed-centred** — dragged by any empty/margin part of itself (the top-centre grip is just the discoverable affordance), but a pointerdown on an interactive control, selectable text or a scrollbar gutter is not a drag, so **prose stays highlightable and links/buttons/inputs stay live**. It snaps to the shared `GRID` lattice, clamps to the viewport, and — given a stable `persistKey` — remembers its spot per overlay. It stays **modal** throughout (scrim, one-at-a-time, scroll-lock unchanged); only placement is user-chosen.
- **`\` toggles the open pane between the user's custom arrangement and the default placement** — a transient, **non-destructive VIEW** (a second `\` restores the custom one; a drag/resize commits a new one and clears it). The floor's regimented `\` is inert while a pane is open, so the two never both fire. Desktop only.
- **A body owns its scroll, never the wrapper** — the pane clips and publishes its on-screen height as the `--gh-h` CSS var; every body sizes its own scroll region against that var, so content scrolls inside while the pinned chrome stays put.
- **Sizing opt-ins are defaults, not settings.** `resizable` adds the bottom-right stretch handle (and demotes `maxWidth` from a cap to an opening width, so a stretch may exceed it); `fillHeight` opens a reading pane tall and immersive; `coverNavRow` makes the reader the ONE immersive pane — it **requires the caller to un-mount the nav row + muster while open** (`WorkspaceView` gates both on `!readerOpen`), and every other pane keeps the row live over it (the §VI navigation invariant). A persisted resized height beats both defaults. Neither affects the mobile sheet.
- **A body that renders flush to the pane edges must clear the pinned handles itself** — no control under the top-centre grip band, none under the resize grip. That covers *static* chrome; content that **scrolls** under the grip needs **`topSeam`**, a short fade of the pane's own background across the top edge, invisible at rest. Don't substitute a `mask-image` on the scroller (it dims at-rest content at the top) or padding alone (the handle then sits on bare background, and a flush hero image still bleeds under it).

**Invariant — the ForallMenu stays crisp above the frost** as the sole nav affordance: it (the ∀ disc + open menu) sits above every Glasshouse layer (*Stacking order*); never blur or dim it. The desktop `all.haus` wordmark to the disc's left is part of the same crisp layer and part of the trigger's click/hover target — a **child of the one lockup container** docked in the nav row, not a separate fixed sibling layer. Per-surface stores follow the `useReader`/`useMessagesOverlay` shape (`isOpen` + `open`/`close`); the body is a shared panel component (`MessagesInbox`, `DashboardPanel`) reused by both the overlay and any standalone page. Spec: GLASSHOUSE-AND-PALETTE-ADR §III.3; WORKSPACE-COLUMN-LAYOUT-ADR §VI.

- **Desktop: the disc never flips to an X for an open pane** (a close-on-click there was mobile bleed) — it always toggles the menu, which renders **over any open Glasshouse**, so Explain is launchable over a pane (pane-mode program, EXPLAIN-ADR amendment 5) and destination-hopping rides the supersede rule. The only desktop X left is Explain's own (About pane open → X closes back to Explain).

This rides a presence registry: `Glasshouse.tsx` mirrors the single live pane's `onClose` into `useGlasshousePresence` (`web/src/stores/glasshouse.ts`, token-guarded like the module-level `activeGlasshouse` so a superseded pane never clobbers its successor); the disc reads `isOpen` to flip the glyph and calls `close()`, and mobile resumes the feed you left underneath. The X **also** shows while the ∀ **menu itself** (or its in-place Search panel) is open — those aren't Glasshouse sheets, so they aren't in the registry, but the disc is their only dismiss affordance on touch (no outside-tap, no panel ✕): `showClose` takes `isMobile && view !== "closed"`, `aria-label` "Close menu". Desktop keeps ∀ while the dropdown is open. A small LIFO back-guard (`web/src/lib/backGuard.ts`, `useBackGuard`) gives each open in-memory dismissible one same-URL `history.pushState` sentinel; a global `popstate` listener closes the topmost guarded surface on Back, and a self-close (✕/Esc/scrim/swipe) consumes its own sentinel via `history.back()` (closes must be idempotent). `Glasshouse` installs it via `useBackGuard(isMobile && !selfHistory, onClose)`; the three URL-synced overlays (reader/profile/surface) pass `selfHistory` to opt out (they manage their own history + `popstate` — `stores/reader.ts` — and would otherwise double-push). The mobile DM cover registers its own guard **above** the Messages sheet's, so the first Back pops the thread to the conversation list and a second closes the sheet (surfaces unmount top-first, so each guard cleans the current top). Desktop is untouched.

**Invariant — one merged Messages inbox (notifications + DMs).** Notifications and direct messages share a single Glasshouse surface, not two overlays: `MessagesOverlay` → `MessagesInbox` (`web/src/components/messages/MessagesInbox.tsx`), three columns on desktop — notifications log (left, `NotificationsPanel`), conversation list (middle, `ConversationList`), message reading pane (right, `MessageThread`, the deliberately narrower column). **On mobile (`<md`) the same surface is two swipeable peer pages** — Notifications and the conversation list — under a segmented header that mirrors the swipe and taps to jump; selecting a conversation pushes the `MessageThread` in as a full-cover layer over the list (`animate-push-in`) that pops back via its back arrow **or a right-swipe** (the iOS-style back gesture, guarded against text-fields / horizontally-scrollable children), so the drill-down never leaves the Messages page and the swipe axis only ever flips the two peers. The dock's own dropdown and its `SearchPanel` ride the same glasshouse material — `bg-glasshouse` (white) + `shadow-lg`, **no border/outline** (lifted by shadow alone, per the no-thin-line rule); rows group find → make → go (Search · create actions · destinations) with a tight 6px gap, muted text at `grey-600`, and the search input sits in a `bg-glasshouse-well` inset well.

**Invariant — one Glasshouse at a time.** Frosted panes never stack: opening any Glasshouse supersedes whichever was open before. Enforced in the primitive itself (`Glasshouse.tsx`, module-level `activeGlasshouse` registry), so every surface participates automatically — including the workspace-local `Composer`/`FeedComposer` driven by local state, not a store. Do not add ad-hoc "close the other overlay first" logic in callers, and do not bypass `<Glasshouse>` for an over-workspace surface (that's the only way to escape the rule). The supersede call is **state-only** (never `history.back`): URL-synced overlays (`reader`/`profile`/`surface`) pass `onSupersede={dismiss}` (a state-only clear) because the newcomer already owns the top history entry — a `history.back` there would pop *its* URL, not the old pane's. Ephemeral overlays omit `onSupersede` (their `onClose` is already state-only). Any new URL-synced overlay must expose a `dismiss` and wire `onSupersede`.

**Retiring a route into an overlay** (the direction of travel — everything that isn't the workspace or an overlay is being retired): keep the old path as a thin redirect shim to `/reader?overlay=<name>[&seed]` so deep links/bookmarks resolve (a client component if it must forward a `#hash`, e.g. `/messages` → `?conversation=`). Routing is centralised in `web/src/lib/workspace/overlays.ts`: `WorkspaceView` reads `window.location.search` once on mount (not `useSearchParams` — it would force a Suspense boundary on prerendered `/reader`), `openOverlayFromParams` opens the seeded store, then strips `OVERLAY_PARAM_KEYS` via `replaceState`. In-app targets point straight at `/reader?overlay=<name>`; for navigations **already inside** the workspace, call `routeToOverlay(href)` first (opens in place, returns true so the caller skips a no-op `router.push`). Refs: `useDashboardOverlay`, `useMessagesOverlay` (the merged notifications + DMs inbox; `?overlay=notifications` redirects into it).

**Invariant — there is no topbar, and no surface reachable from the workspace may escape into a second register.** The black topbar is **deleted** (`components/layout/Nav.tsx` + the orphaned `Footer.tsx`): nothing mounts one, every route is chromeless, and the sole chrome off the workspace is one fixed bottom nav row — `web/src/components/public/PublicNavRow.tsx`, mounted once by `LayoutShell` for any non-workspace route with no pane overlay open. It went rather than being restyled because `/`, `/about` and `/admin/*` had already left it via a `chromelessRoute` allow-list, so the site shipped two houses at once: **an allow-list that grows every time a page is redesigned is a migration in progress, not a design.**

Feed context (skip ears / frame) is lost on a cold reload, so the pane reopens plain.

Do not reintroduce one without a *new* reason; that guard was a hint and never a credential, and was only ever safe because being wrong could hide chrome and nothing else.
- **The escape ban.** A `Link`/`router.push`/`window.location` from any workspace-reachable surface (incl. overlay bodies like `DashboardPanel`) to a platform-prefix or canvas route breaks out of the overlay world — banned. ### Overlay close affordance

Every modal/overlay/panel dismisses via a **floating ✕**, never a text "Close"/"Done" button. Canonical placement is `<Glasshouse>`'s built-in ✕ (top-right, `text-grey-400 hover:text-black`); a bespoke modal puts the same ✕ on a `relative` pane at `absolute right-4 top-4` and reserves clearance (e.g. `pr-12` on the title row). Exceptions: paired action dialogs (`Cancel | Confirm`/`Submit`) keep a labelled `Cancel`; a single-button acknowledgement (`OK`) is a CTA. The rule targets the dedicated dismiss affordance only.

**Escape on a popover over a Glasshouse — claim it via `useEscapeShield`, never a bare `document` keydown.** Glasshouse's Escape-close listener sits on `window`, which fires after any `document` listener in the bubble phase, so a popover/menu/dialog that closes itself on a bare `document` Escape lets the event travel on and ALSO dismisses its host pane (the double-close bug class — SchemeMenu §0i.7, then five more sites §0k.3). The shared hook `web/src/hooks/useEscapeShield.ts` is the pattern's one home: it stops propagation and closes only the topmost surface; its `yieldTo` predicate is for a surface that itself sits UNDER a higher transient modal (AuthorModal → Lightbox — both on `document`, where registration order wins, so yielding, not stopPropagation, arbitrates that pair). Don't reintroduce an inline copy.

### No hairlines, no outlines, no single-pixel anything

Absolute, sitewide invariant. **The site never renders a 1px line, anywhere, ever** — no hairline dividers, 1px borders/outlines/rings, 1px line elements, `<hr>`, or `box-shadow` used as a line. Separation is whitespace and rhythm; emphasis is the 4px slab; structural enclosure, when genuinely needed, is `>= 2px`. No exception for "dense UI chrome" (dropdowns, menus, popovers, settings rows) — that loophole is closed.

Banned, never to be introduced:

- `1px` in any inline style or CSS (`border: 1px …`, `borderBottom: '1px …'`, `box-shadow: 0 1px 0 …`, `outline: 1px …`).
- A bare numeric `1` in a JS style object (`height: 1`, `borderTopWidth: 1`) — React appends the unit, so it renders as a 1px line while greping as nothing. The tripwire gained a pattern for it 2026-07-27, after a divider shipped past the script in the landing-demo bundle.
- Tailwind 1px-resolving utilities: bare `border` / `border-t|b|l|r|x|y`, `border-[1px]`, `divide-x` / `divide-y`, `ring-1` / `ring-px`, `outline-1` / `outline-px`, `h-px` / `w-px` / `h-[1px]` / `w-[1px]`.
- The raw `<hr>` element. Any `hairline` color token used to draw a line.

Instead: **separation** → whitespace (`space-y-*`, `gap-*`) and feed/thread rhythm; **major divider** → `.slab-rule-4` (never hand-rolled `h-[4px] bg-black`); **enclosure/emphasis** where a real border is unavoidable → `>= 2px` (the 2px a11y focus outlines in `globals.css` are correct, not hairlines).

**Failsafe (required before shipping any frontend change):** run the tripwire and treat a non-zero exit for the lines you touched as blocking.

```bash
scripts/check-hairlines.sh            # scans all of web/src
scripts/check-hairlines.sh <paths…>   # scope to the files you touched
```

It greps for every 1px form above (heuristic — read each match). A genuinely reviewed false positive may carry a trailing `hairline-ok` marker with a written reason on the same line; a real hairline must be removed, not suppressed. The repo has pre-existing hairline debt (tracked separately) — for new work: do not add to the count, and prefer to remove any hairline you touch.

### One post per card

A card renders exactly **one** post — never two or more fused. Absolute, sitewide. Relationships between posts (parent → reply, a burst of replies) are expressed by **expanding a card into the thread** (ancestors above, focal, replies below), never by inlining another post's body into a card. Banned fusions, not to be reintroduced:

- **Parent-context tile** — a collapsed reply must not inline its parent above the byline. (Reply context comes from thread expansion.) `ParentContextTile` and `PostCard`'s `header` slot were **deleted** 2026-07-20 — there is no longer a component or a prop to re-mount one with; don't reintroduce either.
- **Reply groups** — a burst of replies sharing a parent must not collapse into one multi-reply card. The gateway feed query emits each reply as its own item; there is no `reply_group` envelope.

Quote embeds are a distinct grammar (a quote *is* one post referencing another) and are exempt. The Quote action is on **all** card tiers, native and external: quoting an external post publishes a native note embedding the origin as a `QuotedEmbed` mini (author · source · excerpt, linked to permalink) — no NIP-18 `q` tag; the reference rides `notes.quoted_post_id`/`quoted_url`/`quoted_source` (migration 102). See UNIVERSAL-POST-ADR.

### Feed card chassis

All three feed card types (`ArticleCard`, `NoteCard`, `ExternalCard`) share a unified grammar:

- **Left bar**: 4px solid, full height. Black (`#111111`) native, crimson (`#B5242A`) paid, grey-300 (`#BBBBBB`) external. `borderLeft` inline + `paddingLeft: '24px'`.
- **Byline row**: mono-caps 11px — that is `.label-ui` (`text-grey-600`), never hand-rolled. Order: TrustPip · Author · middle-dot · timestamp · (optional price or protocol badge). While trust is parked the `TrustPip` is a **decorative dot** (`aria-hidden`, no title/cursor) that opens nothing — the click-to-open `PipPanel`/`PipTrigger` are **dormant, not deleted** (restore by reinstating the `PipTrigger` branch + `onPipOpen` in `PostByline`). The per-feed author/source actions it used to host moved to the byline hover panel (next bullet).
- **Byline routing** (same rule on cards and on every expanded parent/reply): a byline links to the internal all.haus surface, never the origin platform. Native → writer profile (`/{username}`). **Tier-A/B external** (carrying an `external_authors` record — nostr pubkey, atproto DID, activitypub actor) → `/author/:authorId` (UNIVERSAL-POST-ADR §4.4). **Tier-C/D external** (rss/email, `post.author.id` null) → **plain text**, no link. The only route out to origin on a card is the source-attribution line. Every linked byline (native + A/B) opens a debounced, session-cached `AuthorModal` (`type="author"` → `GET /author/:id/profile`); inside it the display name links internally (`profilePath`) and — A/B only — the `@handle` links out to origin (`externalUrl`: bsky.app / actor URI / njump.me, built by `gateway/src/lib/author-resolve.ts::buildExternalProfileUrl`). The modal is the one byline affordance routing to origin. The hover panel also hosts the **per-feed VOLUME control** (`SourceVolume`, `web/src/components/feed/SourceVolume.tsx`) — the 5-step weight + RANDOM/TOP sampling, shown only for **sources you follow**: native authors via the `/author-volume/:pubkey` route (pubkey threaded from the byline), external sources via `patchSource` on the resolved `feed_sources` row (the same universal by-feed-source-id path the FeedComposer uses; absent row ⇒ not in this feed ⇒ no control). This replaced the parked pip panel's volume bar. Reachability is hover-only (no touch path — mobile tunes volume in the FeedComposer).
- **The byline row is also the card's DRAG HANDLE** (drag-a-source-into-another-feed). Card text is selectable, and a `draggable` element swallows the mousedown that starts a selection, so `web/src/lib/dragSurface.ts::isDragSurface` resolves draggability per pointerdown — but "bare chrome only" leaves a target that is real and invisible (the padding ring and the gaps between rows), which is how the gesture was lost for a fortnight after `82274a8`. So a caller may nominate a handle: `isDragSurface`'s optional `handleSelector` (chassis passes `CARD_DRAG_HANDLE_SELECTOR`) makes a marked region grab **even though it holds its own text**, with controls inside it still winning because the walk hits `NO_DRAG_SELECTOR` first. The byline is the honest handle — the gesture moves the SOURCE and the byline is what names it — and it carries `cursor: grab`, the only thing on the card that says so. Scoped to `level="feed"` (thread ancestors/replies share the host's `dragData`, so a handle there would move the wrong source) and to **every density** (a tightened card has no bare chrome left, and condensed/headline is where curation happens). The drop side: the origin feed is published for the gesture's life via `web/src/lib/workspace/cardDrag.ts` (`dataTransfer` is unreadable during `dragover`, so without it every vessel arms — including the one the card came from, which is what buries the real targets); the origin stays unarmed and real targets ring in `palette.crimson`, never `palette.walls` (that is the merge-armed answer, and on two of four sides it paints the wall its own colour).
- **Action row**: mono-caps `text-mono-xs` + `tracking-[0.02em]` (rem, so it scales with the global type size — never `text-[11px]`). `Reply` opens the compose overlay; `Quote`, `VoteControls`, `BookmarkButton`, `ShareButton` per type.
- **No avatars** in card bodies — left bar + pip + mono-caps name carry identity.
- **Feed rhythm**: each `PostCard` carries its own `marginBottom` (no wrapping `space-y`), per `GAP_PX` in `web/src/lib/post/level-spec.ts` — **8px** between independent items, **5px** within an expanded conversational chain. (The legacy `components/feed/` card stack is retired — FEED-RETIREMENT Slice 7; only the shared `AuthorModal` and `SourceVolume` survive there. Legacy `PlayscriptThread` still uses `space-y-[32px]`.)

### Reply threads (playscripts)

Threads render flat and chronological as a transcript — never nested indentation, left borders between replies, quote-of-parent blockquotes, or avatars. Component surface: `PlayscriptReply` + `PlayscriptThread` in `web/src/components/replies/`; `ReplySection.tsx` flattens the nested API tree into `PlayscriptEntry[]`.

- **Step-in**: thread container indented 32px once (`ml-8`) from the parent's content column — the only indentation in the system.
- **Rhythm**: 32px (`space-y-[32px]`).
- **Speaker line**: mono-caps 11px. `TrustPip` · bold Jost name · colon. Own replies read `YOU:` with no pip (the asymmetric 16px left-jog is deliberate). Non-adjacent parent: prefix `→ PARENT:` in `grey-400` + 16px gap, then `NAME:`.
- **Dialogue line**: Jost 14.5px (`text-[0.90625rem]` — rem so it scales; never the old `text-[14.5px]`), `leading-[1.55]`, black, at `mt-1`.
- **Vote count**: `VoteControls` pinned top-right, aligned to the first dialogue line.
- **Action row**: `time · REPLY · DELETE · REPORT`, mono-caps 11px `text-grey-400`, revealed on hover/focus (optional `#fafaf7` tint).
- **Pagination**: first 10 entries + `SHOW N MORE REPLIES` (mono-caps, grey-400, underline on hover).
- **Workspace focal node + parents-above**: an expanded conversation reads strictly top-down — focal in the middle, **ancestor chain above** (one flat `ml-8` indent, never a deepening cascade), descendants below. No separate pinned card or duplicated byline. **Clicking any ancestor/reply re-roots in place** (repeatable); **clicking any quote tile — native or external — focuses the quoted post** (in a thread it re-roots; on a **collapsed feed card** it expands the quoted post directly as the focal of a fresh conversation, distinct from a body click that expands the host — the external path's context-only `feed_items` twin is minted by the gateway on demand; in-place focus always wins over the origin permalink, which stays reachable from the focused post's own source-attribution line — 2026-07-09, closing the native-quote gap): every host that mounts an interactive card wires `onQuoteOpen` (WorkspaceView `expandQuote`, `PostThread` → `thread.reroot`, `SourceSurface`/`AuthorProfileView` `expandQuote`) — a new card host must too, or its quote tiles go inert; **clicking the focal collapses the card**; `↑ Full conversation` returns to the opened item. **Rich focal, light context** (native + external): the focal always renders its full rich body (content, media, action row) — including after re-rooting; ancestors/replies render as lightweight playscript. **No left bar is ever drawn on a focal node.** Re-root is one engine for native + external (`usePostThread.reroot`): pure client-side when the node's subtree is in the pool, fetch `/thread/:id` + merge when not (a failed fetch reverts the focal, never a broken derive). Byline routing as in the feed chassis. Wiring (`PostThread`/`usePostThread`/`level-spec.ts` — the legacy `ConversationView`/`ExternalAncestorRail` engine is retired) and full behaviour: `docs/adr/UNIVERSAL-POST-ADR.md` (+ CARD-BEHAVIOUR-ADR addendum 2026-05-30).
